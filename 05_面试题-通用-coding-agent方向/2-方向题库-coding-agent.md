# 方向题库 · Coding Agent 基座


---

## 一、数据合成与任务构造

### Q1. 训练任务怎么合成的？三件套在训练链路里怎么用？


回答：三件套 = **issue（problem statement）/ golden patch（参考解）/ test patch（测试）**。合成路线两条：**真实 PR 挖掘**（从仓库 commit 历史筛"同时含 code patch 与 test patch"的提交，issue 取 commit message/关联 issue，改写为自包含题面——去仓库特定指代、补上下文）与**模型合成**（往健康代码注入缺陷再生成修复，可控制难度与语言分布）；生产级流水线通常以真实挖掘为主干、合成补语言/难度缺口。链路用法：issue 作模型输入；test patch 提供**可执行判分**（F2P/P2P，见 Q2）——它是 RL reward 与评测的共同判据；golden patch **绝不能出现在模型可见的输入里**（题面、检索环境、测试文件都要查泄漏——golden 的代码片段可能被模型从 issue 或检索结果里找到，需做相似度检测），用途限定为入库 oracle 三重校验（见 Q2）、泄漏检测与覆盖率锚点、人工对照；蒸馏/SFT 的监督对象是执行校验过的 teacher 轨迹，golden 只在构造 patch 级 SFT 样本时作答案段且须配推理链。题面质量本身要过 rubric：描述是否自包含、可复现、不含解法（解法泄漏是 SWE-bench 系数据 30%+ 的已知问题）。

**问题（追问）：issue 改写怎么保证不失真？**

回答：改写后用 solver 回验：参考模型分别按改写前、改写后的题面各采 n 条解题，改写后 F2P 翻转率不显著下跌（跌幅超阈值判失真）才入库；辅以题面对照——从原 issue 归纳行为断言清单（症状、触发条件、期望行为），改写版须全覆盖且不得新增解法提示。

**问题（追问）：合成注入缺陷和真实缺陷分布差多远？**

回答：合成偏"局部语法/单点逻辑"，真实偏"跨文件语义"；用混合配比并对齐真实任务的文件跨度分布。

**问题（追问）：数据量与语言分布？**

回答：全链路量级按三级给出——候选 commit 10⁴~10⁵ 起筛，执行校验通过率约 30~50%（Q4 口径），质量过滤后再折损；公开参照 SWE-bench 从约 9 万 PR 筛出 2,294 实例。语言分布按 top5 列占比并与业务语言结构对齐（按本人项目实测替换）。

### Q2. F2P / P2P 校验各验证什么？为什么两重都要？


回答：执行校验在打 patch 前后各跑一次测试，形成两组判定：**F2P（FAIL_TO_PASS）**——修复前失败、修复后通过的测试，验证"这组测试确实检测目标缺陷"（否则测试与缺陷无关，任何补丁都能过）；**P2P（PASS_TO_PASS）**——修复前后都通过的测试，验证"补丁没有破坏既有功能"（回归防线）。只做 F2P 会放进"修了目标但弄坏别处"的假修复；只做 P2P 会放进"什么都不修"的空补丁（原测试本来就过）。实现细节：每组测试在仓库镜像内自动执行（build→apply patch→run pytest），执行结果按超时/编译失败/断言失败分类——**编译失败≠测试失败**，环境问题要和断言问题分开打标，否则环境噪声会进 reward。reward 构成：F2P 全过 ∧ P2P 不掉 = 满分；部分通过的加权口径（F2P 权重 > P2P）也常见，但要防"只修一半拿高分"的退化，通常 F2P 采用一票制。

**问题（追问）：oracle（golden patch）校验和它什么关系？**

回答：入库前用 golden patch 跑三重校验（F2P 翻转 + P2P 保持 + golden 可复现），保证任务本身可解且判分可信；训练时模型 patch 只跑 F2P/P2P。

**问题（追问）：测试超时算过还是不过？**

回答：单独类别，不算通过也不算失败，从该样本剔除（环境问题不惩罚模型）。打标时与模型侧超时分开：rollout 超长是模型行为、按软惩罚口径处置（见 Q16），环境侧超时是基建问题、整条剔除并可回流重跑；监控面板盯环境失败率，超阈值先修基建再训练。

### Q3. 测试断言约束不足与过约束怎么识别与治理？


回答：公开基准的实证——SWE-bench+ 人工审计约 **31% 的"通过"属弱单测可疑通过**、另有 32% 存在解法泄漏(SWE-bench+ 的审计）；UTBoost 给弱单测实例补强测试后新检出 15~28% 的错误 patch。失效模式四类：**断言约束不足**（仅断言不抛异常或返回非空，恒真断言占比高）、**检验目标偏移**（测的是 patch 顺带改动而非目标行为）、**断言过约束**（绑定实现细节——错误消息全文、内部调用序列，语义等价的正确实现被误判失败）、**解法泄漏**（测试内联了 patch 逻辑，等于用实现验证实现）。治理流水线按执行成本升序三层（层间硬淘汰）：**层1 静态规则**——断言数量/类型统计（恒真断言占比阈值）、patch 覆盖率（test 执行是否触达 code patch 修改行，SWT-Bench 将 golden patch 覆盖率作为正式指标）、泄漏检测（test patch 与 code patch 的 token n-gram/AST 相似度）；**层2 执行变异**——变异测试（对被修函数注入算子替换/边界偏移/条件取反等变异体，重跑测试统计 kill 率，存活变异体多=约束弱）、**对抗补丁探针**（构造不解决 issue 的补丁——空补丁/只改注释/对示例输入硬编码特判，任一探针能通过即判弱单测）、等价实现交叉验证（LLM 生成语义等价但写法不同的正确补丁，被误判失败=断言过强）；**层3 语义对齐**——把 issue 归纳为行为断言清单（输入/触发条件/期望输出/边界），对每个测试函数归纳被测意图，逐条匹配算规格覆盖率；再加失败症状一致性（未打 patch 的 base 上跑测试，失败输出与 issue 描述的症状比对）。

**问题（追问）：变异测试成本多高？**

回答：每个实例 ×N 个变异体 ×全测试重跑，只对入库前的候选任务跑（一次性成本），并限制变异体数量（用 LLM 生成与缺陷类别相关的少量定向变异体）。

**问题（追问）：如果只能做一层？**

回答：对抗补丁探针性价比最高——空补丁、只改注释、硬编码返回值任一通过即判弱单测，直接对应"假通过"这个最致命的失效（RL 里一条假通过就是一条错误正奖励）；静态规则（恒真断言占比、patch 覆盖率）几乎零成本可以先跑，变异测试与语义对齐是增强项不是准入项。

**问题（追问）：RL 里弱单测的后果？**

回答：错误正奖励成为 reward hacking 的直接入口：空 patch 或硬编码返回值的候选同样拿到通过奖励，组内归一把这种假高分变成基线，带歪同组其他样本的优势符号，模型学到"骗测试"而不是"修缺陷"。蒸馏侧同样受害——拒绝采样只留"通过"轨迹，弱单测会放行没真正解决问题的轨迹进 SFT 数据。所以弱单测治理（三重校验+对抗探针）放在数据准入段，而不是训练期补救。

### Q4. 某类任务效果差要补数据——怎么从海量 GitHub 仓库找到有用的？


回答：判别特征建漏斗、执行成本逐层升序。**粗筛（元数据/规则，近零成本）**：语言与框架匹配、仓库健康度（star/活跃度/CI 配置存在性——有 CI 说明测试文化好）、结构信号（commit 同时含 code+test patch、issue 与 commit 可关联）、规模上限（巨型 mono-repo 构建成本高先排除）。**中筛（轻量解析）**：测试框架识别（pytest/jest/go test）、测试密度（测试文件/源文件比）、issue 文本质量（长度、是否含复现步骤、是否自包含）。**精筛（执行校验，贵）**：只对通过前两层的候选跑 docker 构建 + F2P/P2P 三重校验；执行是瓶颈（单实例分钟级），所以漏斗的设计目标就是把执行量压到候选量的几个百分点。定向补某类任务时，把"类型"转成可过滤的判别特征——如补"跨文件重构类"，筛 commit 的文件跨度分布；补"某语言"，在粗筛层直接开关。

**问题（追问）：构建成功率多少？**

回答：量级口径（典型 30~50% 的候选能成功构建可判分环境），失败原因分类（依赖缺失/超时/私有依赖）与自愈手段（依赖预装、缓存镜像、重试）。

**问题（追问）：怎么防止同质化（一个仓库挖出几百个相似任务）？**

回答：按仓库限额 + 任务级去重（题面+patch 相似度聚类，每簇限量）。

### Q5. 任务太简单、模型训完做不了实际任务——难度分布怎么定？


回答：**以可学习区间为中心设计难度分布，用基准对齐度封顶**。①难度度量用参考模型/SFT 模型的 pass rate（多采样估计），把任务池分桶（<10% 难 / 10~40% 中难 / 40~70% 中 / >70% 易）；RL 训练集以中档为主体（有梯度信号），保留部分难任务供探索、少量易任务稳定梯度；SFT 阶段可以更偏易-中（可模仿）。②"实际任务对齐"检查：合成任务与真实业务任务在**任务结构**（单文件/跨文件/repo 级）、**依赖复杂度**、**测试密度**三轴上对照，缺口定向补（比如业务是 repo 级多文件修改，而数据 90% 是单文件——这是分布性缺陷，加再多量也没用）。③难度上限锚定评测集：自建评测的难度分布应覆盖业务难度上界。④随训练推进滚动重标难度（与动态采样联动，见《0-通用基础题》group size 题）。

**问题（追问）：怎么知道是"任务太简单"还是"能力上限"？**

回答：看分难度桶的 pass rate 变化：易桶接近饱和且难桶长期零通过=数据缺难样本；各桶都不动=训练信号或 reward 有问题。

### Q6. 合成 benchmark 和真实任务接近吗？泛化怎么验证？


回答：验证方法而非口头保证：①**结构对照**——任务结构/文件跨度/依赖复杂度/测试密度四轴的分布对比（合成 vs 真实留出集）；②**迁移实验**——合成数据训练 → **真实任务留出集**评测（关键：留出集绝不进训练，最好来自私有仓库或时间切分后的新 commit，防污染）；③**误差分析**——失败案例按"分布内没见过这类结构 / 推理能力不足 / 工具使用错误"归因，第一类占比高就是泛化问题、加结构多样性而不是堆量；④防"在公开 benchmark 上过拟合"——公开集只作横向对标，且要查污染（题面与预训练语料的重合检测）。

**问题（追问）：时间切分怎么做？**

回答：训练任务的 commit 时间全部早于某日期，评测任务取之后的新 commit（真实世界的新任务天然无污染）。

### Q21. 缺陷注入合成怎么做？为什么不直接改写仓库既有 issue？


回答：注入合成的定位是补真实 PR 挖掘的分布缺口，相对"改写既有 issue"有三条独立理由：**覆盖**——自然 PR 的缺陷密度由社区节奏决定，长尾语言与长尾仓库题量少，头部库又已被公开数据集吃掉；**产量可控**——注入按每仓固定配额产出（如每仓 5 条），实例量与难度分布可设计，量级参照：约 1,850 仓 × 每仓 5 条 ≈ 8,000 条候选实例；**真值自洽**——注入的缺陷自带反向补丁，反向应用即 golden patch，F2P/P2P 真值直接可得、不需要人工判定。注入两路并行：**AST 规则改写**（改运算符、删边界判断、调换参数顺序、改异常分支）——确定性强、成本低、注入位置可精确到符号，但缺陷模式可枚举、模型容易识别是人为构造；**LLM 改写**——给目标函数与缺陷类型，要求只改一个语义单元、其余保持不变，产出用 AST diff 校验改动范围，能产出"改对了但没改全""异常处理漏一支"这类更自然的长尾缺陷。**五类配额**按真实漏洞分布设：边界条件、运算符与比较、异常与错误处理、类型转换、状态与并发；约束单仓配额覆盖不少于三类、同一函数不重复注入——防一个仓库挖出一簇同质任务。两路产出统一过三项准入（注入补丁打上后目标用例必失败、反向补丁打上必全过、既有用例不回退）加不稳定用例剔除，与真实 PR 走同一条校验链路。

**问题（追问）：注入缺陷的分布怎么跟真实缺陷校准？**

回答：用真实 PR 的缺陷分类做配额目标而不是凭直觉设：抽样真实 merged PR 的 code patch 按五类打标，得到各类占比作为注入配比的锚。校准指标用 solver 行为一致性——参考模型在注入任务与真实任务上的动作序列分布对比（先跑测试再修与先定位再修的比例、复现动作占比、平均轮数），分布显著偏离就调配额。已知偏差形态：注入偏"局部语法/单点逻辑"、真实偏"跨文件语义"，所以文件跨度分布要单独对齐（见 Q22）。

**问题（追问）：这类合成数据直接做 RL 有什么问题？**

回答：行为单一化——注入缺陷的观察面收窄到 F2P/P2P 两组用例，模型容易学成"上来先跑测试、哪个挂修哪个"的固定套路，探索与定位行为退化（SWE-smith 类数据的已知问题）。SFT 阶段问题不大（模仿目标是正确轨迹），RL 阶段要三手缓解：混入真实 PR 轨迹并按**动作序列多样性**配比（不是按条数配比）、给定位类与复现类动作单独补样本、reward 里加对定位与复现过程的中间信号（目标用例状态翻转、关键文件被正确识别）——只靠终态 0/1 会把行为压回先跑测试。

### Q22. 跨文件、repo 级的高难度任务怎么构造？


回答：真实 PR 过滤后分布天然偏"单文件、小改动"，补难度两条路：①**PR 合并合成**——让强模型基于仓库上下文把语义相关的多个 PR（同一特性、同一重构）合并成一道跨文件、跨模块的大改动量任务，强迫多步定位与跨文件修改，配套生成合并后的 issue 与测试文件，产出完整三件套；②**注入扩跨度**——缺陷注入不限单函数，按调用图选多个相关函数同时注入。两条路的产出都必须回真实校验链路：合并任务的 F2P 取各子 PR 用例并集、P2P 取交集，oracle 校验合并补丁整体可复现；合并不是拼接——子改动之间没有语义关联时题面无法自洽改写，直接弃。难度标签用双信号：静态特征（改动文件数、diff 规模、跨文件依赖深度、issue 到修复点的定位距离）加行为特征（教师多路采样通过率）。业务对齐检查与 Q5 同口径：合成任务与真实业务任务在文件跨度分布上对照——业务是 repo 级多文件修改而数据 90% 单文件，是分布性缺陷，加量无用。

**问题（追问）：怎么从失败轨迹反推是任务链路的哪一环不行？**

回答：失败归因按链路环节分桶：**定位错**——patch 落在无关文件（与 golden 改动文件比对即得）；**方向对没修完**——F2P 部分通过；**修对但引入回归**——P2P 掉；**环境与工具错误**——调用失败率异常。桶占比决定补数据方向：定位错补代码理解类任务（函数定位、调用链追踪、影响面分析，这三类可以用 AST 静态分析程序化造题、规则判分、天然有标准答案）；修不完补难度配额；回归多补带验证收尾习惯的轨迹示范。归因的前提是失败打标在 rollout 时就落盘，事后靠人工翻轨迹归因不可规模化。

### Q23. 仓库原生测试不够，让模型自己写测试用例可信吗？


回答：合成测试是补充不是主干——量级口径：仓库原生测试（从 PR 的 test diff 提取）为主体，模型合成补"PR 只改代码没改测试"的缺口，占比约 15~20%。可信度风险三条：**按答案写测试**——生成时看到 golden patch，测试内联了解法（等于用实现验证实现）；**恒真断言**——只断言不抛异常或返回非空，任何补丁都过；**目标偏移**——测的是顺带改动而非目标行为。治理三层：①**信息隔离**——测试生成只给 issue 与被测接口、不给 golden patch，生成后做 test patch 与 code patch 的 token n-gram/AST 相似度泄漏检测；②**执行校验**——合成测试与原生测试过同一套三重校验（F2P 翻转 + oracle 全过 + P2P 保持），外加对抗补丁探针（空补丁/硬编码返回值能过即弃，同 Q3）；③**rubric 校验**——correctness（断言与题面语义一致）、determinism（重复执行结果稳定）、edge-case 覆盖，逐项打分低于阈值整组重生成。边界要说清：合成测试的证明力低于原生测试（原生测试经过人工 review），高价值评测集不用合成测试判分。

**问题（追问）：怎么判断一个测试是不是"按 issue 写的"？**

回答：跑 F2P/P2P 时不看 issue、只 apply patch，所以"测试与 issue 一致"必须单独校验：把 issue 归纳成行为断言清单（症状、触发条件、期望行为、边界），对每个测试函数归纳被测意图，逐条匹配算规格覆盖率；再加失败症状一致性——未打 patch 的 base 上跑该测试，失败输出与 issue 描述的症状比对，对不上就是测错了目标。

### Q24. Terminal/命令行类任务的数据怎么构造与验证？


回答：terminal 任务与 SWE 的结构差异决定构造方法不同：SWE 有结构化目标（patch）与强验证（单测），terminal 是自由命令序列、弱验证、长程探索。构造按类目分三型：**环境配置**（装依赖、配服务，配套检验脚本验证最终状态——如断言包版本、服务可起）；**环境修复**（在健康环境里程序化注入破坏——删文件、改配置变量、改目录权限，任务是恢复，验证器对比修复后状态与健康快照）；**文件批处理**（格式转换、批量文本处理，产物与参考答案内容比对）。判分用 **state-based** 而不是过程判分：只校验环境末态（文件存在性、内容哈希、命令可执行、服务可达），不约束命令序列——同一末态有无数条合法路径，约束过程会惩罚合法探索。合成走 taxonomy inside-out（先定义能力类目树再按类目造题）加三重验证（题面自洽、验证器正确、任务可解），量级口径：合成存活率约三分之一（参照口径 33.6%），即造三条留一条。低成本来源是 SWE→terminal 跨格式转换——把"改代码修 bug"转成"用命令行定位并修复"的终端形态（参照口径 10 万级任务）；与 SWE 混训的相互影响见 Q12。

**问题（追问）：state-based 判分怎么防骗？**

回答：状态断言要断言"结果"不断言"痕迹"：只查文件存在的任务会被 `touch` 骗过，断言要落到内容级（哈希、可解析、语义抽查）；写操作类任务用前后状态差分校验（环境快照对比，实际改动集合与期望集合比对）；破坏注入型任务天然防骗——恢复要求被破坏的功能真实可用，重跑健康检查通过才算修复。

## 二、执行环境与沙箱

### Q7. 可执行环境怎么构建？镜像怎么组织？


回答：镜像分两层——**语言基础镜像**（python/node/go 各自的依赖与构建工具链）→ **仓库镜像**（在语言镜像之上 clone+安装依赖+预热测试，每个任务一个）；两层都可缓存复用（语言镜像全局共享、仓库镜像按任务缓存）。构建流程自动化：拿到任务先**识别语言/框架**（文件特征或让 agent 判），选对应基础镜像→装依赖→跑一遍原测试确认环境健康（P2P 基线通过）→固化成判分镜像。**构建成功率**是数据生产线的核心指标（典型值与 Q4 同口径：30~50% 的候选能建成可判分环境），失败分类与治理：依赖私有源（换公共替代或弃）、构建超时（分层超时预算：安装/编译/测试分别限时）、网络依赖（构建期允许、判分期断网，保证 reward 可复现）。规模：容器池 + 任务队列、按语言隔离资源、镜像分层共享磁盘；数字口径：日均执行量与判分成功率。

**问题（追问）：为什么判分期要断网？**

回答：模型在训练环境学会"联网搜答案"是 reward hacking（推理侧不存在此途径或口径不同），且测试结果可复现性要求环境确定性。

**问题（追问）：镜像膨胀怎么治？**

回答：分层+定期 GC 冷任务镜像、用 registry 缓存、任务结束后容器即销毁只留判定结果。

### Q8. 沙箱超时/初始化失败进了轨迹怎么办？


回答：**区分"模型错"与"环境错"，环境错误不进策略梯度**。模型不该为基建故障负责——环境失败的样本如果按"任务失败"给负 reward，模型会学到虚假的负关联（且污染组内基线）。实现：执行日志按错误类型打标（模型断言失败/超时/环境初始化失败/网络故障），环境类整条剔除或重试；RL 侧在组内统计前先过滤环境失败样本（该组不足则补采）；监控面板盯环境失败率——**失败率超阈值先修基建再训练**，否则有效 batch 规模缩水、训练吞吐虚降。另一个细节：模型侧超时（rollout 超长）与环境超时要分开打标，前者是模型行为（见 Q16 的软惩罚口径）、后者是基建问题。

**问题（追问）：环境失败的 prompt 永久丢弃吗？**

回答：不，环境修复后可回流重跑（任务本身没问题），维护"可判分任务池"与"环境健康状态"两张表。

### Q9. 并发执行怎么设计？吞吐多少？


回答：**沙箱池（预热容器复用）+ 任务队列（优先级调度）+ 判分 worker（拉取结果跑测试）**；关键设计点：①容器生命周期（冷启动秒级~分钟级，池化预热消掉）；②资源隔离（CPU/内存限额防单个任务拖垮宿主，磁盘配额防测试写满磁盘）；③超时熔断（安装/编译/测试三段独立限时）；④失败重试策略（幂等任务可重试，非幂等标注后丢弃）。数字口径：并发容器数、日均执行实例数、端到端判分成功率、平均单任务判分时长。参考锚点（按项目实测替换）：单容器 4C8G 起步、单宿主并发几十~上百；池化预热把冷启动从分钟级压到秒级；pytest 判分单任务中位分钟级，端到端判分成功率（剔除不可构建任务）目标 ≥95%；日吞吐 ≈ 并发数 × 86400 / 平均判分时长，按语言分池隔离资源。

### Q25. 环境构建失败怎么分类？构建成功率怎么拉上去？


回答：失败按四级打标——**依赖类**（私有源、版本冲突、系统库缺失）、**超时类**（安装/编译/测试分层超时）、**测试类**（测试收集不全、F2P 不成立——测试本身抓不到缺陷）、**资源类**（磁盘、内存、端口）。量级口径（按项目实测替换）：失败构成中超时约 45%、F2P 不成立约 20%；分语言成功率悬殊——解释型（Python）约 47%、C++ 约 18%、Swift 约 5%，生态越碎片化成功率越低。拉升手段按层排布：**预筛**——小模型按仓库静态特征（CI 配置、依赖声明完整度、测试目录、README 构建指引）预测构建成功概率，低分跳过，参照口径可把成功率提约 2 倍；**自愈循环**——构建 Agent 在沙箱内循环"构建→诊断报错→装缺失依赖/改配置→重试"，参照口径成功率 67%→80%（另一参照：对零通过的 near-miss 仓库做 hint-in-the-loop 两阶段恢复，16.5%→57.2%）；**降级**——构建不出的任务按降级等级标记入库（用更粗的判分口径）或回流单点排查，不直接丢弃。工程底座是微虚拟机快照：Docker 冷启动约 2,750ms，内存快照恢复约 150ms（约 16 倍，写时复制让数千实例共享基础快照），支撑构建 Agent 的高频干净重试——每次重试从干净快照重拉，不用从头装。

**问题（追问）：构建 Agent 的权限边界在哪？**

回答：只允许改环境层——依赖版本、构建脚本、环境变量、包源；禁止改业务源码：环境构建的目标是把仓库原样跑起来，改源码等于作弊、污染任务真值。识别手段：workspace 文件哈希白名单（只放行构建/配置文件路径）或 git diff 路径过滤，改动落源码路径即拒绝；Agent 修改全部留痕可回滚，同一路径连续失败 2~3 次即中止换策略。构建成功的判据是执行门而不是"脚本跑完没报错"：编译型语言要求编译通过且测试可执行、改动进入最终编译产物，解释型要求测试可发现、可执行、结果确定。

### Q26. 整仓测试跑不动，判分时的测试子集怎么选？


回答：整仓测试中位数可达数百条（参照口径：整仓中位 812 条、单实例判定 6.8 分钟），RL 每个训练步要判数百个候选补丁，必须选子集。选法是对受影响模块做依赖闭包：对每个源文件做 AST 解析，抽出 import 三种写法建模块级有向图，从 code patch 改动模块沿反向边做一次 BFS 得受影响集合，测试文件的 import 关系命中受影响集合即入选——比按目录选准确，按目录会漏跨包集成测试、也会带进同目录无关用例。参照口径：执行用例中位数 812→47，单实例判定 6.8→1.9 分钟。静态依赖图追不到三类动态依赖——importlib 动态导入、插件注册（entry points）、测试内 monkeypatch 打桩——由白名单强制补入；白名单不是估出来的：抽 2,000 个候选补丁同时跑整仓与子集判定，不一致案例逐个回溯归因，把涉及模块加进白名单后一致率做到 99% 以上。兜底纪律：未选中用例定期（如每 24 小时）全量复核一次回收漏判——否则子集判定就成了为快而放松回归检测。

**问题（追问）：flaky 测试（时过时不过）怎么办？**

回答：每条候选用例重复执行 5 次，结果不一致判为不稳定并从判定集合剔除（参照口径：剔除率 3.4%）。检出率推导：偶发失败率 p 的用例重复 n 次被发现的概率是 1-(1-p)^n——p=0.3、n=5 时约 83%；加到 10 次剔除率只多零点几个点但耗时翻倍，5 次是成本折中。不稳定来源五类：依赖当前时间或时区、未固定随机种子、访问网络、并发端口或临时目录冲突、测试间执行顺序依赖——前两类固定时钟与种子即可消除，后三类只能靠重复执行统计。flaky 用例混进判分的后果与弱单测同构：真修复被判失败就是一条错误负奖励。

## 三、轨迹与蒸馏

### Q10. teacher 怎么选？蒸馏轨迹质量怎么保证？


回答：teacher 选型三轴：**任务通过率**（在目标基准实测，不迷信榜单）、**工具调用规范性**（是否稳定输出可解析的 action 格式）、**成本**（按 token 计价的通过率/成本比）。质量保证三层：①**结果校验**——轨迹最终 patch 必须过 F2P/P2P（执行判定，不是"看起来对"）；②**过程校验**——行为审计：工具调用序列是否越界（teacher 偷偷查外部资料？环境断网+调用日志审计）、答案与检索内容的重合度（防照抄）、中间步骤的独立性（关键决策点不能是"恰好"的跳跃）；③**best-of-n 选优**——每任务采 n 条（4~8），执行判分后只留通过轨迹，多条通过时按"步骤最短/最少无效探索"选示范。SFT 数据与 RL 数据的分工：蒸馏轨迹（teacher 生成、已验证）进 SFT 冷启动；RL 阶段用学生自采样（on-policy），两者数据格式同构但来源严格区分。

**问题（追问）：teacher 和学生模板不一致怎么办？**

回答：蒸馏前把 teacher 输出重格式化到学生模板（动作格式转换要逐字段映射并抽检），模板不一致是训推不一致的常见来源（接《0-通用基础题》训推不一致题）。

---

### Q11. 怎么防学到 teacher 的 hack 技巧？


回答：**teacher 的环境必须与学生训练环境同构**：同样的工具集、同样断网、同样超时预算——teacher 在宽松环境里生成的"聪明捷径"（查外部文档、调用学生没有的工具）学生会照学，而学生推理时没有这个口子。审计手段：①工具调用白名单校验（轨迹中出现未授权工具即整条剔除）；②**hack 检测器**——针对已知模式做规则扫描（测试文件写入、答案与检索片段高重合、跳过验证直接提交）；③抽样人工审（按任务分层抽 1~5%，看关键决策步骤的合理性）；④对抗验证——用"去掉该技巧后能否通过"做反事实检查（如禁止查看某文件后重跑，还能过=修复能力真实；不能过=依赖了环境捷径）。发现 hack 轨迹后的处置：剔除 + 回溯同批次的审计 + 把该 hack 模式加入检测器规则库（持续积累）。

---

### Q12. SWE 任务和 terminal 任务混合训练过吗？效果如何？


回答：两类任务的结构差异：**SWE**——结构化目标（patch）、强验证（测试）、相对短的交互轮次；**terminal/命令行交互**——自由序列（任意命令组合）、弱验证（无单测，靠环境状态或最终产物判）、长程探索（轮次多、上下文滚动）。混合的实验结论形态：正向——命令行能力反哺 SWE 的环境探索（定位文件、复现 bug 的 shell 技能）；负向——长程探索行为挤占 SFT 学好的"直接精准修复"模式，动作空间互相污染（patch 动作 vs 命令动作的分布此消彼长）；治理——**动作空间按任务类型条件化**（任务类型 token 或路由头）、分阶段课程（先 SFT 结构化、再混入探索型）、配比消融（如 3:1/1:1/1:3 三档扫描）。关键是自己项目的消融数字；没有消融就如实说明"观察到 X 现象、未做严格归因"。

---

### Q13. think 内容的质量怎么评估？坏的推理链怎么发现？


回答："结果对但过程错"（碰巧通过、跳步猜中）是过程数据的核心风险，发现手段：①**多轨迹分歧定位**——同任务采多条通过轨迹，按步骤对齐，分歧步（各轨迹做法差异大的步骤）重点审；②**步骤独立性验证**——对关键中间结论做反事实检查（去掉该前提，后续推理是否仍成立）；③**answer-think 一致性打分**——最终答案与思考链的结论一致性（think 里说 A 答案给 B 是强噪声信号）；④**决策点抽样人工审**（分层抽关键决策而非随机抽）。发现坏链后的处置：整条弃 / **局部重写**（定位最早坏步，从该步重新生成后续——保住前段合格部分）；坏链不是全无价值——可作 DPO 负例或过程奖励模型的对比信号。

---

### Q14. 失败轨迹怎么利用？


回答：按失败原因分桶利用：①**环境失败**（见 Q8）——不利用，剔除；②**模型能力不足的诚实失败**（推理方向对但没走通）——三条路径：**渐进提示救回**（在失败点注入提示重新生成，救回的轨迹带"提示标记"降权入训）、**失败点定位+局部重生成**（保前段）、**作负例**（DPO 偏好对的 rejected / 过程奖励模型的负样本）；③**hack 型失败**（作弊被抓）——剔除且进检测规则库，不作负例（hack 轨迹作负例有"教模型识别作弊"而非"不作弊"的歧义风险，谨慎表述）。定位最早出错 token 的实操：逐步回放（把轨迹前缀逐段喂回模型看哪一步后的分布突变）或分叉重生成（从第 k 步分叉重采，二分定位责任步）。

**问题（追问）：失败轨迹直接给负 reward 不行吗？**

回答：会惩罚"探索了但没成功"的行为，模型学会保守（只做最有把握的），伤害探索；GRPO 组内对比天然给"同题更差的解"负优势，比全局负例更温和精确。

### Q27. 多 harness/多框架的轨迹怎么统一进训练？


回答：不同 Agent 框架（Claude Code、OpenHands、Cursor、Codex 等）的原子工具差别大——搜索有的有专门代码检索工具、有的只有终端 grep；编辑有的用片段定位、有的用行号或全文替换；原子工具数 4~9 种不等，消息结构与调用协议也不同。多框架接入的目的本身是泛化：让学生见过各种工具范式、能快速适配新 harness。落地做法是 schema 归一：定义统一训练格式，工具名、参数、返回结构逐字段映射，同时保留各框架的调用特征与行为分布——归一不是抹平成一种。映射正确性要起真实 server 对比 rollout 验证，不能只看框架源码：edit 类工具格式不对称（片段定位对行号全文），静态改写容易改错。训练侧两个口径：工具描述与参数 schema 写在 system 段、训练时可见，模型按上下文里的描述选工具而不是靠记忆；环境返回文本 mask 出 loss，但教师轨迹里的工具调用（工具名与参数）计 loss——这条线的目标正是学会什么时候调哪个工具、参数怎么填。

**问题（追问）：工具幻觉怎么治？**

回答：工具幻觉的定义是调用了不在当前工具列表内的工具、或参数不符合 schema 的调用，按轨迹粒度统计占比。根因是训练数据里工具列表的数量、顺序、组合相对固定，形成位置伪相关——模型按记忆假设工具存在与排布，而不是读当前上下文的工具表；暴露方式很典型：接入新框架评测，工具数相同只是顺序不同，幻觉率就明显升高。治理是工具列表乱序加随机丢弃，迫使模型依赖真实工具表，参照口径幻觉率 20.5%→7.6%；残余未归零的原因：模型容量限制、语义相近工具混淆（Grep 与 Glob）、干预覆盖不足。判分期还有一道硬门：格式不合规的调用被 verify 拦下直接计失败（同 Q15 的格式合规硬门）。

---

### Q28. 百万级轨迹怎么去重？怎么证明过滤没误删好数据？


回答：直接 O(N²) 相似度会算爆，管线按成本递增、覆盖递减三层排布：①**格式清洗**（近零成本）——工具名跨 harness 标准化、剔除未正常结束与超 cost limit 的轨迹，先砍最大量；②**工具调用序列过滤**（O(N)）——去无效调用与连续重复调用，规则级去重；③**近重复剔除**（O(N²)）——只对清洗后的小集做，SequenceMatcher 相似度阈值 0.9 加 n-gram（n=5）重复率 >20% 命中。相似度的对比对象是 loss mask=1 的模型自生成 token，不是整条轨迹原文——工具返回与环境观测是注入内容，混入会污染相似度（同环境返回让不同轨迹假相似、不同返回让同解法假相异）。质量评估另起一路：评判器模型按行为合规、任务完成度、安全、事实正确四维打分，每条独立评 5 轮多数投票——用 5 倍推理成本换误判率大幅下降，在"数据质量决定训练上限"的场景划算；超长轨迹按消息边界截断并标记，不直接丢弃，避免系统性丢失长任务信号。

**问题（追问）：过滤把某一类数据偏好性删掉了怎么发现？**

回答：每一轮过滤做 before/after 多维分布对照：任务类型分布、语言分布、来源 harness 分布有没有移位，辅以 TF-IDF 加 PCA 二维投影看形态——只有分布形态基本不变，才能判定删的是离群点而不是整个子分布。特例分流："正确但没用上工具""轨迹过短但高分"这类样本不进 SFT 主池但也不丢，分流到更早的阶段（如 mid-train）并补 turns、token 数元数据。过滤强度本身也要消融：激进过滤配置在多 epoch 下会反跌（参照口径 -7.9pp），说明过滤有收益上界，强度以消融为依据，不是"觉得不好就删"。

### Q29. 验证器（verifier/选优器）怎么训？只用成功轨迹会怎样？


回答：验证器的判别信号来自执行结果而不是人工偏好：正例取执行通过的轨迹，负例取执行失败的真实轨迹并按失败类型三类分层——补丁应用不上、目标用例未修好、既有用例被破坏，与正例按约 1 : 1.5 : 1 混合（"未修好"最难判、配比最高），标签从判定日志直接读、标注成本为零，不做人工构造负例。只用成功轨迹训会退化成给文本流畅度打分——条理清楚、表面合理的轨迹被判高分，接进 RL 就是典型的 reward hacking 入口。一个容易做错的口径：验证器要在**策略模型的候选分布**上训——用 SFT 后策略模型自采的候选（如每题 16 条）训，而不是用教师轨迹训；教师的错误模式与行为特征跟策略模型不同，训出来的判别器在策略候选上判别力下降。评测用同题正负配对排序，参照口径：难分样本（正负得分差小于 0.1）判别准确率 61.3%→78.5%，不分层对照只有约 70%；另报与人工判定的一致率。配比边界：负例比例继续抬高（如到 2.0）准确率还能微涨，但选优指标反掉——负例太多验证器偏保守，把正确候选也判死。

**问题（追问）：验证器在数据侧与推理侧各怎么用？**

回答：两个位置分开。**数据过滤器**——rollout 阶段筛掉低质轨迹、把预算投给有效样本，是拒绝采样的前置。**测试时选优**——候选生成完后排序提交最高分；成本控制是按序评估，当前最高分不低于阈值（如 0.9）且领先第二名足够幅度（如 0.15）即提前提交，阈值在留出集按分位数标定，参照口径：平均评估条数 16→8.6、成本降约 46%，依据是统计上约 73% 的题正确候选出现在前 4 条。报数三项并列：单次正确率、pass@k、选优后正确率（如 38.5% / 72.4% / 47.7%），归一化 (47.7-38.5)/(72.4-38.5)≈0.27——选优只拿到理论收益的两成多，选优器质量是 test-time scaling 的瓶颈。接进 RL 当软奖励时要给上限（如 0.4）并随训练退火，否则模型会发现骗过验证器比修缺陷省事。

## 四、训练与评测

### Q15. 代码 RL 的 reward 怎么设计？只有测试通过够吗？


回答：主干必须是**可执行 outcome**（F2P 全过 ∧ P2P 保持 = 1），这是不可妥协的锚——没有它其他一切 shaping 都会漂。但只有它不够，补三类辅助项并说清克制理由：①**格式合规硬门**（patch 可解析/可 apply/动作可执行——不可解析直接负分或 0 分，这是合法性不是偏好）；②**过程效率项**（无效探索轮数、无关文件改动数的轻惩罚）——权重刻意小，防止模型为拿效率分而牺牲主目标；③**防 hacking 项**（修改测试文件直接判负、答案与检索原文重合度惩罚）。克制原则：**shaping 项总数 ≤3、权重和远小于 outcome**——每加一项 shaping 都在开一个新的可利用奖励缺陷，reward 设计的成熟度体现在"敢少加"而不是"加得多"。消融口径：每项单独去掉看主指标与 hacking 率变化，无差异的项删掉。

**问题（追问）：reward 稀疏怎么办？任务通过率很低时组内全零。**

回答：接动态采样与难度分层（见 Q5 与《0-通用基础题》group size 题），代码任务还可以用"F2P 部分通过比例"做稠密化（但注意部分通过的语义歧义——修一半可能是错的方向）。

---

### Q16. rollout 超长被截断怎么处理？


回答：把截断样本记 0 分，模型无法区分"答错"与"没答完"——负信号会教模型**尽早放弃**（学会短答案避免超长惩罚），直接伤害长链推理。处置三选一（按实现成本）：①**软惩罚 shaping**（DAPO 的 Overlong Reward Shaping）——超长样本给按剩余长度衰减的预设惩罚而非 0，保留"长但没完成"与"短而错误"的区分度；②**剔除不进梯度**——超长样本整条移出 batch（不惩罚不奖励），配超长率监控防长任务系统性缺席；③**根因治理**——max_response_length 与任务难度分布匹配（多轮 agent 任务 8K/16K 常见），超长率本身是探针：持续 >10% 说明长度预算或任务难度失衡。

**问题（追问）：截断检测在哪做？**

回答：rollout 引擎层（生成到 max token 即标记 truncated），与 EOS 自然结束严格分开打标，混标会让惩罚口径失真。

---

### Q17. 评测集怎么构造？为什么不全用公开 benchmark？


回答：评测分两层——**公开集**（SWE-bench Verified/Lite 等）做横向对标——可比性强但有三个缺陷：**污染**（仓库公开、可能进预训练语料——需时间切分+题面与语料重合检测）、**分布偏窄**（Python 为主、repo 时代偏旧、单文件任务占比高）、**弱单测问题**（见 Q3，SWE-bench+ 已实证）；**自建集**对齐业务任务分布（语言/框架/任务结构/难度四轴对齐），私有仓库天然无污染，规模上"几百个精心校验的任务"优于"几千个没跑三重校验的"。自建集的纪律：入库前 golden 三重校验（Q2）、定期换血（防训练数据随迭代渗透）、区分 dev/test（dev 可用于早期 stopping，test 只在里程碑跑）。**模型推理时禁网**是评测纪律的一部分——评测环境与线上能力口径一致。

**问题（追问）：怎么证明自建集无泄漏？**

回答：任务来源与训练数据源的仓库名单隔离 + 题面/patch 与训练集的相似度扫描（n-gram + embedding 双检）。

---

### Q18. 训推不一致在 coding agent 上有什么特殊体现？


回答：agent 场景在三个通用来源（模板/采样/异步）之上叠加两类特殊形态：①**环境状态回放不一致**——多轮交互的上下文重组：训练 rollout 记录的轨迹在重放/评测时逐 token 重组，工具返回的格式化（空格、转义、截断）与线上 harness 的实际返回有差；对策：训练 rollout **直接用线上同款 harness 生成**（训练-推理同构），而不是训练侧单独实现一个简化版环境。②**completion_mask 口径两端不一**——训练时哪些 token（工具返回、系统提示）被 mask 出 loss，推理时的上下文组装是否保持同样的拼接与模板；对策：模板与 mask 配置用同一份配置文件生成两端代码（single source of truth）+ 逐 token 对拍测试进 CI。

---

### Q19. 通用旗舰模型已经能写代码了，为什么还要做 coding 专用模型？


回答：三条正交论据：①**深度**——专用模型在目标基准与真实通过率上超同代通用线（口径：同基座下 SWE-bench Verified solve rate 高 X pp，按项目实测填；垂直能力上限来自数据配比与 RL 任务的定向投入，通用模型把容量分摊在全世界）；②**成本**——专用线可以用小参数（如 7B/32B 级）达到业务可用的通过率，推理成本比大通用模型低一个量级，高并发场景（IDE 补全、CI 修复）成本差是决定性的；③**可控与迭代**——数据飞轮自主（业务回流数据定向训，迭代周期周级，通用线以月/季计）、合规与行为可控（改动范围约束、私有化部署）。边界：能力天花板依赖通用基座（专用线通常从通用线 mid-train 分叉而不是从零训）；通用模型代际跃升会压缩专用线的生存空间，所以专用线要持续绑定业务数据壁垒。

---

### Q20. pass@k 和 dynamic sampling 有什么区别？


回答：**pass@k 是评测指标，dynamic sampling 是训练机制**。pass@k 衡量"采 k 次至少一次通过"的概率（无偏估计 $\hat p = 1 - \binom{n-c}{k}/\binom{n}{k}$，n 为总采样数、c 为通过数）——k 越大反映能力上限与多样性，用于模型评比对；dynamic sampling 是 DAPO 的训练手段——过滤零梯度组并补采，优化的是训练信号的密度。两者可以对话：训练中如果 pass@8 长期=0 的任务（太难），动态采样永远采不到有效组——所以要配难度分层（Q5）；pass@k 高但 pass@1 低的任务，恰是 RL 最有提升空间的中频任务。混淆点常在"都用多次采样"——一个衡量分布的性质、一个改变训练的输入。

---

### Q30. 训练集与评测集之间的污染怎么防？


回答：防污染三件事同时做。**仓库级切分**——训练集与评测集按仓库不相交，不做同库换题：同仓库不同任务仍有泄漏，模型见过代码风格与测试写法。**时间切分**——训练任务的 commit 全部早于某日期，评测任务取之后的新 commit：真实世界新任务天然无污染，且能兜住基座预训练已见过旧代码的情形——基座若见过评测仓库，评测数字没有意义，所以要么选未见过该数据的基座、要么明确只用时间切分的后段。**重合检测**——题面/patch 与训练集（及可得的预训练语料）做 n-gram 加 embedding 双检；golden patch 的代码片段单独查，它可能从 issue 描述或检索结果里漏进模型可见输入。两个实操点：**评测禁网**——联网评测会混入"搜到原 issue/PR"的假能力，有实证是模型联网评测时推理到一半转成背诵答案、断网评测掉约 10 个点；**公开集本身要质检**——公开 benchmark 存在错题型问题（环境损坏、参考答案错、测试自身错，参照口径：SWE-bench Pro 人工抽检发现百余道问题题），直接用会污染"何时开 RL、效果如何"的判断；评测集被刷到顶失去区分度时也要换更难、防污染的集。自建私有集的纪律见 Q17。

**问题（追问）：时间切分之后旧任务还能用吗？**

回答：能。旧 commit 进训练池、新 commit 进评测池，滚动执行——每次基座换代或评测集换血时按新的知识截止时间重切一刀。配套资产是"评测集仓库名单"这张表，数据采掘侧把它当黑名单过滤，防止训练迭代中无意识地把评测仓库的数据采回来。

### Q31. 长程任务（几十上百轮连续工作）怎么训？一上来就跑长任务行不行？


回答：直接上长 horizon 会 reward 稀疏致死——64 轮起步时绝大部分轨迹失败，组内全零无梯度。标准解法是 horizon 课程：从短程逐档解锁（参照口径 5→15→30→64→128 轮），每升一档先用成功轨迹做小规模 SFT 冷启动（1~2K 条，可用较弱模型的成功轨迹）把该档的初始通过率拉起来再开 RL，每档 pass rate 进平台期作为升档信号。配套三个工程点：①**窗口形态一致**——长程任务推理时一定会出现"上下文里只剩摘要"的形态，训练时没见过就是未定义输入，压缩后段样本要与完整前段样本按比例混合训练；②**超长处置**——轮数或长度上限外直接判失败还是做 summary 续推是能力判定的取舍，参照口径：超出长度上限（如 256K）即判失败、不做续推，代价是丢掉"长时执行能力"这一类任务的区分度；③**信用分配**——一两百轮只有一个终态奖励时按阶段而不是按动作打分：用可执行信号把轨迹切成意图定位、复现确认、修复实施、验证收尾四段，每段只给一个由关键事件触发的奖励项（正确文件被识别、目标用例由通过转失败、由失败转通过、既有用例不回退），一两百轮压成 4 个奖励项，权重按段级事件对终局成败的判别力（用历史轨迹估计信息增益）配；段级分数作为 advantage 塑形项加在对应 token 段上并做退火，防模型为拿过程分表演里程碑。token 级 PRM 不用：标注成本随轮数线性涨、dense 分极易被攻击、相比可执行判据没有精度优势。

**问题（追问）：长程任务的评测怎么做？**

回答：终态 0/1 之外加三类过程指标：成功任务的成本（轮数、token、工具调用数）、无效动作占比（重复调用率——同一 （工具， 规范化参数） 对在短窗口内再次出现）、超时与截断率。长程任务单独成桶报告，不能被短任务的高通过率平均掉。对标"数小时连续工作"的形态时，任务集要含跨会话续跑（上下文重置后凭摘要继续），评测口径是续跑后首个操作的有效率（不重复已做操作、参数可执行），而不是单会话通过率。

### Q32. 多域混训（SWE/Terminal/WebCoding/WebSearch/General）会互相干扰吗？


回答：会，跷跷板有实测参照：SWE 与 WebCoding 混训时 SWE benchmark 掉 2~3pp、WebCoding 美学评分掉 4~5pp——长程编辑的梯度挤占视觉精细化容量；Terminal 与 SWE 混训影响较小（共享代码理解底层能力），但 Terminal 特有的跨格式命令行推理仍被稀释。域的划分依据两条：能力维度正交性（SWE=长程代码编辑加测试验证，WebCoding=视觉美学加交互保真，Terminal=命令行状态追踪，WebSearch=检索加摘要综合，General=指令跟随）与混训消融的跷跷板证据。两种解法：①**分域独立训 Expert 再融合**——各域独立达峰后按域路由做 on-policy 蒸馏融合，规避权重平均的灾难性遗忘与多域联合 RL 的梯度冲突；②**必须混训时的工程补偿**——channel 差异化 loss 权重：SWE 轨迹 3K~10K token、QA 类 200~500 token，按 token 等权时短样本数量多、累积梯度压过长样本，按域设 loss 系数（长轨迹域大于 1、短样本域小于 1），让各域对总梯度的贡献与能力重要性成正比而不是与 token 数成正比，系数在 dev set 上按各域消融指标定。判断口径：跷跷板是否成立要按域分桶报指标——总分不跌、单域跌 5pp 也是干扰。

**问题（追问）：什么时候选独立 Expert 再融合，什么时候直接混训？**

回答：看域间共享底层能力的比例与部署形态：共享高（SWE 与 Terminal）混训成本低，冲突大（SWE 与 WebCoding）且算力允许时独立 Expert 上限更高；单模型部署诉求强的，蒸馏融合比权重合并稳。

## 五、行为与泛化

### Q33. 训练中轨迹越变越长、重复操作变多，是什么信号？


回答：先区分两类行为退化。**轨迹膨胀**——结果仍正确但步骤低效（重复无害操作、过度验证）：终态 0/1 reward 下轨迹变长不改变 episode reward 这个标量本身，代价在别处——单位成功成本上升、有效动作比例下降、超时概率上升，极端时 pass rate 反降；如果看到"reward 涨而轨迹变长"，先查 reward 里是否混入了过程分或长度分，那不是能力提升。**重复与自循环**——模型在相同代码状态下重复执行等价操作（搜过的内容再搜一遍），成因是长轨迹下状态跟踪失效：对已执行操作的记忆随上下文增长衰减。监控口径：把每次工具调用归一化成 （工具名， 参数规范化哈希） 对——参数规范化含路径转绝对、空白统一、去多余引号——统计相邻重复与全局重复占比（参照口径：相邻重复约 9.7%、全局重复约 18% 即需治理）；另一个行为探针是工具级熵——正常任务 search/edit/test 调用有自然比例，某工具占比畸高（9 次 search 配 2 次 test）说明策略在坍缩。治理双层：数据侧把教师轨迹的冗余操作过滤或掩码；训练侧 rubric 的效率维度让重复步受罚，并显式训练环境状态跟踪行为（不重复执行已生效命令）。红线判据：reward 涨、评测集不涨甚至跌，是 reward hacking 嫌疑——抽 top/bottom reward 轨迹对比，按复合 reward 的各分量定位被刷的那一项。

### Q34. 合成数据训完，模型在真实任务上的行为模式会偏成什么样？


回答：已知偏差形态两种。**行为单一化**——合成缺陷的观察面收窄到判分用例，模型学成"上来先跑全量测试、哪个挂修哪个"的固定套路，定位与复现的探索行为退化（真实工程师先读 issue 复现症状）；**错误模式错位**——合成数据覆盖不了真实生产的错误分布（环境异常、依赖问题、含糊需求），纯合成训练在真实使用中暴露训练时看不到的失败类型。检测手段：在真实任务留出集上对比动作序列分布——先测试与先定位的比例、复现动作占比、平均轮数——与合成任务上的分布对照，偏移显著即行为被合成分布塑形。缓解三手：混入真实 PR 轨迹并按动作序列多样性配比（不按条数）；给定位、复现类动作补样本并加中间信号；按真实漏洞分布扩充缺陷类型配额（同 Q21 的校准）。合成数据的作用是补长尾与控难度，不是替代真实分布——这条边界要在消融里证明而不是口头声明。

### Q35. 线上回流数据怎么进训练飞轮？


回答：合成数据保量不保分布，回流数据保真不保量，两者分工互补。飞轮闭环：上线 → 用户使用产生真实轨迹 → 日志回流 → 质量、满意度、严重度打标 → 好轨迹反哺 SFT、坏轨迹转专项处理（构造纠错样本或进 RL 负例池）→ 二阶段续训 → 再上线。入库前做噪声体检四维：错误级联（一步错步步错的传染段）、工具幻觉、相邻重复、全局重复——口径与离线轨迹治理（Q28）复用。两个设计点：①**回流轨迹的可判分性**——线上任务没有隐藏测试，判分降级为规则加评判器混合（末态校验、格式合规、评判器四维分）；能从真实 issue 反构出可执行环境的，优先转回可判分形态再入池。②**防飞轮自污染**——模型自产数据占比设上限并与人工、教师数据分桶监控，连续多代自产数据训练会放大自身偏差；每代续训在独立人工评测集上卡门槛，不过门槛不发布。要报的指标：回流有效量、代码相关率、严重 bad case 占比、二阶段续训带来的基准提升。
