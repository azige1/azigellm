## 零、高频基础概念

**Q0.1：你说的「等价性判分」，和一般的「让模型生成测试用例」有什么本质区别？**

A：本质区别在**判分依据**。常规做法让模型生成「输入 → 期望输出」对，模型需要预判函数的输出——非平凡函数的边界行为（空字段保留、Decimal 舍入、惰性求值）很容易被预测错，错的期望值一旦入库，整条链路的判分噪声就固定下来了。等价性范式里模型只写「怎么比对」：断言候选实现与参考实现在相同输入下行为一致、异常类型与消息一致（允许子串匹配）。原函数就是 oracle，不需要任何人「知道正确答案」。另外我们加了一道**自等价校验**：新测试先在参考实现上自跑，不通过即判测试自身缺陷、入库前拦截（实测拦截约 **7%**），把「测试 bug」与「实现 bug」在语义上分开。这是它和一般生成方式的第二个区别：生成质量有确定性兜底。

**Q0.2：参考实现当 oracle，如果参考实现本身有边界 bug 呢？**

A：这是这套协议成立的前提，要分三层回答。第一，**任务形态决定了影响可控**：我们产出的任务要求「复现参考实现的行为」，而不是「修正它」——参考行为就是规格的一部分，判分是自洽的。第二，**素材端筛掉了低质对象**：种子仓库取中高热度、持续维护的项目，且函数要经过依赖切片可解析、测试可执行的准入。第三，**如果确实要训练「比参考更好」的行为**，这套判分就不适用——那属于 SWE 修复类任务（issue 驱动的行为变更），判分依据换成测试翻转（F2P/P2P），是另一条链路。所以我从没把等价性判分描述成万能协议，它的适用边界很清楚：**行为复现类任务**。

**Q0.3：长轨迹训练里 loss mask 怎么配？为什么环境返回的 token 不计 loss？**

A：按消息角色配：**assistant 消息计 loss，user 与 tool 结果不计**。原因很直接——loss 是在教模型「该生成什么」，环境返回的内容（文件内容、测试输出、命令回显）不是模型的决策产物，把它计进 loss 会教模型去「复述工具输出」。我们曾见过两类反向案例：一类是中间助手文本全计 loss，模型学成「在该调工具的地方自言自语」；另一类是工具返回被计 loss，模型开始输出伪造的回显内容。具体到多轮样本，还有一个**结构不变量**：`assistant.tool_calls[].id` 与后续 `tool.tool_call_id` 必须一一配对，切分、注入、打包任何一步破坏配对，样本只能整条废弃（我们一批切了 **130 余段**，靠切点落轮界保证零孤儿）。

**Q0.4：你说「答案获取」行为要一票否决——训练数据里这类行为怎么检测？**

A：判定口径只认**实际执行**的工具调用，而不是全文本匹配。具体是遍历 `tool_calls` 里的命令与 URL 字段：出现目标包的下载、上游源码获取、判分材料读取这类**实际执行动作**才算命中（token 等价匹配，不是子串包含）。全文本匹配的误报率很高——配置里写着 `git clone` 的安装指引、提示词里作为反例出现的禁止命令，都会被误伤；曾经有一批「举报」，改用工具调用字段判定后全部消失，都是误报。检测到信号的轨迹**一票否决**（不进训练集、不进修复队列），因为答案获取行为在训练里的收益是「虚高分」，会把模型教成绕过问题而不是解决问题。

**Q0.5：长任务里的上下文压缩是怎么发生的？压缩之后模型为什么容易退化？**

A：压缩发生在推理侧的运行框架里：上下文逼近窗口上限时，框架把较早的对话折叠成一段摘要、只保留最近若干轮原文，模型后续看到的是「摘要 + 最近消息」。退化来自两个病理：一是**记忆盲改**——模型凭对旧代码的记忆直接编辑，没重读文件，改动基于过期状态；二是**重读泥潭**——反复读同一批文件却建不起任务状态。我们对照测过：压缩过的轨迹中位得分大约只有未压缩组的一半。所以训练侧要做两件事：把「压缩后先重读、先验证」的行为教进模型（这类样本要专门合成），以及在压缩点附近的样本里保证恢复动作是「重读/验证」而不是「接着盲写」。

## 一、项目一：真实仓库代码的函数级任务合成与等价性判分

### 开场概览

**Q1.1：用三句话讲清这个项目——输入是什么、输出是什么、核心难点是什么？**

A：输入是 GitHub 上的真实 Python 仓库代码和仓库级元信息（star、LOC、模块结构）；输出是**带自动判分能力**的函数级编程任务，形态是「签名 + 自然语言规格 + 隐藏测试」，下游可以直接用于模型评测或 SFT/RL 训练。规模是从 **210 余个**仓库抽取约 **4.6 万个函数**，最终产出 **1.4 万条**经沙箱验证可判分的任务。核心难点有三个：判分要可信（我们用「参考实现行为等价」替代「预测期望输出」）；上下文要经济（依赖切片替代整仓供给）；合成质量要可达标（生成-执行-反馈闭环 + 覆盖率双门槛，三轮把达标率从 **45%** 提到 **87%**）。

**Q1.2：这批任务最终谁在用？上下游分别是什么？**

A：下游有三类消费。评测侧：给「签名 + 规格」让模型写实现，跑隐藏测试得到可比较的分数，且按仓库维度切分评测集与训练集（防记忆虚高）。训练侧：作为可验证任务进 SFT/RL 池，判分结果直接当奖励信号。数据侧：任务本身是「判分即奖励」的干净样本，规避了开放式生成任务的奖励建模难题。上游是仓库采集（种子筛选）与执行环境（沙箱判分设施）；我做的是中间的合成链路：抽取 → 上下文构建 → 测试合成 → 闭环判分 → 打包。

**Q1.3：你在这个项目里具体负责哪些模块？**

A：我负责**等价性判分协议**与**依赖切片上下文**两个模块的设计与实现——前者包括自等价校验流程、容器化判分口径与噪声白名单；后者包括语句依赖图 + 调用图的切片算法与深度参数调优。另外参与了运行时插桩数据回填的实现验证、生成-执行-反馈闭环的流程实现，以及规格提炼与任务打包环节。

### 递进追问链

**【追问链 1：等价性判分】**

**L1（是什么）：你的判分协议具体长什么样？**

A：测试代码不含字面期望值，形态是把候选实现与参考实现放进同一执行环境做对比断言：

```python
def test_normalization_is_equivalent(candidate, reference):
    cases = ["", "  a  ", "A\u00a0b", "line\nbreak"]
    for c in cases:
        assert candidate.normalize(c) == reference.normalize(c)
```

异常路径同型处理：断言两边异常类型一致、消息一致（或允许的稳定子串）。浮点返回按等值浮点比较，复杂对象比较序列化结果。每条测试入库前先跑**自等价校验**——在参考实现上执行，不通过就拦截。

**L2（为什么）：为什么这个协议比「直接写断言期望值」好？**

A：两个层面的收益。质量层面：判分噪声的来源被切掉了——期望值写错是系统性噪声，且两个方向都有危害（真实现被误判错、错实现被误判对），它会以「数据质量问题」在训练里持续放大。成本层面：模型不需要「理解输出该是什么」，只需要写对比逻辑，这个任务对模型的能力要求与「生成器的能力」错位更小，合成成功率显著更高。还有一个隐性收益：自等价校验给了一个**确定性的质量门**——不通过直接拦，不占用人工审核预算。

**L3（怎么做）：自等价校验具体怎么跑？和判分是同一套设施吗？**

A：同一套沙箱执行设施，两个用途。流程是把「仓库 + 函数 + 测试」三件套提交进隔离容器：先做环境准备（代码挂载、依赖就绪），再初始化（编译/导入检查，把 `SyntaxWarning: invalid escape sequence`、`NameError: ` 这类初始化噪声列白名单——环境噪声不该计入测试失败），最后提交运行，回收逐测试的通过状态与日志。自等价校验就是把「候选实现」指向参考实现的同一套执行；判分时把「候选实现」换成模型产出。两者共用一套服务，区别只在挂载的实现对象。

**L4（failure mode）：这套流程在真实跑的时候出过什么问题？**

A：三个典型。其一，**测试自身的期望写反**：早期没上自等价校验时，一批测试断言的是「错误行为」，判分时把正确实现全部判错——上线校验后这类在入库前拦掉。其二，**环境相关失败混入**：部分函数依赖系统库或数据文件，容器里初始化就失败，表现为「收集期报错」——如果不区分「测试逻辑失败」和「环境初始化失败」，会系统性压低所有模型分数；处理是把初始化失败单列一个状态，进人工复核而不用作判分。其三，**判分容器里的路径口径**：候选自己写的打包配置（`pyproject.toml`）会改变导入路径，导致判分测到它自己的目录结构、绕开要求——处理是判分前清除候选的打包配置与自写测试目录，统一用固定 `PYTHONPATH` 口径。

**L5（边界/未做）：这套判分的局限是什么？如果给你更多时间会改什么？**

A：局限有三条。一是**只适用于行为复现类任务**——涉及「改变行为」的任务（修 bug、加功能）不适用，那些需要 F2P/P2P 式的测试翻转协议。二是**依赖参考实现的稳定性**——参考实现如果依赖外部服务/时间/随机性，等价对比会不稳定，这类函数目前直接不产任务（被准入过滤掉）。三是**覆盖率与判分强度的关系**——我们把「分支覆盖率 ≥0.8」当质量门槛，但覆盖率不等于契约强度（高覆盖率测试可能只覆盖 happy path）。如果继续做，方向是给测试加**契约强度分层**：区分「覆盖了多少分支」与「断言了多少可观察行为」，对边界行为（异常、空输入、边界数值）单独统计覆盖，优先保这类。另外就是把判分服务做热容器池化，把单次判分的环境准备成本压下去。

**【追问链 2：依赖切片】**

**L1（是什么）：依赖切片切的是什么？**

A：切的是**执行闭包**，不是文件。从目标函数出发：函数体内引用的名字（辅助函数、常量、类）沿语句依赖图找定义；跨文件的引用经调用图（PyCG）解析到实际定义；递归展开到闭包边界（默认 3 层深度）。加上必要的 import 语句（外部包保留 import、不展开源码），产出一个「最小可运行上下文」——它包含的信息足够理解这段代码在做什么，但去掉了仓库里的其余噪声。

**L2（为什么）：为什么不直接喂整个仓库，或者按文件截断？**

A：整仓的问题是双向的：token 成本高（大文件几千到上万 token），噪声大——测试合成需要理解的是目标函数的行为，而整仓上下文里混着几百个无关函数，模型经常引用到同名但语义不同的邻近工具函数。按文件截断是个「物理切法」：跨文件依赖多的函数会缺符号（生成引用不存在的名字）；单文件巨大的函数仍然超长。切片是**按执行语义切**：它保证「执行到的东西都在里面」且「不执行的东西不在里面」——这是它相对两种朴素方案的本质优势。

**L3（怎么做）：切片遇到的边界情况怎么处理？**

A：主要三类。动态引用：`importlib` 动态导入、`getattr(obj, name)` 反射这类静态分析追不到的引用——保守策略是把动态导入出现的模块整体纳入切片，无法解析的名字进保留白名单，以可控的上下文膨胀换取执行期不缺符号。装饰器与类继承：类方法切片时把父类定义与装饰器依赖纳入。模块级副作用：模块顶层的初始化逻辑（注册表、常量计算）要跟着定义语句一起带上，否则运行环境不一致。这些边界情况的处理成本不低，但比「缺符号导致生成失败」便宜得多。

**L4（failure mode）：切片构建率或质量出过什么问题？**

A：有过一次「切片过深」的教训。早期默认深度设得大（接近全闭包），一些「工具函数引用了大半个仓库」的函数把闭包拉得很大，切片上下文反而逼近整仓规模。改成 3 层后这类函数要么被截断到一个合理上下文（配合白名单兜底），要么进入「难测函数」类别自然淘汰。另一类是**切片返回空**：目标函数只依赖外部库的，几乎没有内部依赖——这其实是好事（上下文可以极简），但分析器对这种情况返回空切片会让下游误判为「切片失败」，后来把「空切片」与「失败」两个状态分开。

**L5（边界/未做）：切片方法的根本局限是什么？**

A：它依赖静态分析的召回率。纯动态结构的代码库（大量运行期拼装的引用）切片质量会退化，只能靠保守兜底把上下文放大。另外它没有做**跨语言泛化**——目前只针对 Python 的解析与调用图，换成静态类型语言（Java/Go）理论上更简单（类型系统提供更多依赖信息），但工程上要重写解析层。如果重做，我会把切片器做成可插拔的接口（类似我们现在对「整仓上下文」与「切片上下文」双策略的切换），让新语言接入只补解析器、不改进程。

**【追问链 3：生成-执行-反馈闭环】**

**L1（是什么）：闭环几个环节、以什么条件收口？**

A：四步循环：generate（对未达标函数生成或修复测试）→ execute（批量送沙箱执行）→ filter（按结果分流）→ update（更新工作清单），直到「分支覆盖率 ≥0.8 且达标函数占比 ≥0.8」或达到轮数上限（3 轮）。分流规则三档：通过且覆盖率达标 → 出列；通过但覆盖率不足 → 打回并附覆盖率提示；未通过 → 打回并附异常栈。

**L2（为什么）：为什么要给两类不同的反馈信号？**

A：因为两类失败的病因不同、修复动作也不同。执行报错是「测试写坏了」（API 打错、数据不合法、环境问题），模型需要看到异常定位（类型、消息、出错行）去修测试；覆盖率不足是「测试写浅了」（只跑 happy path），模型需要看到未覆盖的分支结构（分支位置、条件表达式、已覆盖/总数）去补边界用例。给同一种反馈（比如只报「未通过」）的话，模型会两种病用同一种修法，修不对就反复重试，轮次预算烧在无效循环上。

**L3（怎么做）：覆盖率提示是怎么渲染的？为什么不用「你把没覆盖的地方补上」这种自然语言提示？**

A：渲染成结构化提示：未覆盖分支的位置、条件表达式原文、当前覆盖数/总数。用结构而不是笼统自然语言，是为了让模型的补测动作**指向具体的代码路径**——「分支在 line 42，条件是 `if not sep.strip()`」这种信息可以推出需要什么输入；而「补上没覆盖的地方」只会让模型加更多 happy path 断言。实测上，带结构化覆盖率提示的一轮修复成功率明显高于纯报错回传，这也是把达标率从 45% 推到 87% 里后两轮的主要来源。

**L4（failure mode）：闭环跑挂过吗？什么问题？**

A：有过「重复送容器」的成本问题：第一版实现每轮把全部函数重新打包送进沙箱，后两轮里已经达标的函数占了很大比例，容器成本随轮次线性涨。改成「仅未达标子集增量执行」后，后两轮容器成本压到首轮的一成上下。另一个问题是**理论上无限循环的可能**：个别函数生成器永远修不好（比如依赖外部网络的函数），如果门槛是「全对才收」就会把重试预算全耗在长尾上——用达标比例门槛（0.8）给循环一个确定的出口，长尾自然淘汰。

**L5（边界/未做）：这个闭环有什么结构性局限？**

A：它是**单侧反馈**——反馈只来自「测试执行」，没有任何关于「任务本身是否值得做」的判断。一个函数如果本质上不可测（随机性、外部依赖），闭环会规律性地浪费几轮预算才淘汰它，没有任何机制把它提前挑出来。改进方向是用**可测性先验**做预筛：静态特征（是否含 IO/网络/时间调用、是否有参数注入点）预测「这个函数的测试最终能否达标」，把明显不可测的跳过闭环。另外现在覆盖率只算分支覆盖，没有对异常路径、边界值单列覆盖统计——它们是「高质量测试」与「跑得动的测试」的核心差异，值得单独设指标。

### 设计决策与取舍

**Q1.4：为什么不用「模型预测期望输出 + 人工抽检」的路线？既然最终都要人工抽检，两套成本差不多吧？**

A：抽检的成本结构完全不同。预测路线的问题是**错误分布不均匀**：非平凡函数上错误率高、简单函数上错误率低，抽检按比例抽的话，错误恰好集中在抽不到的非平凡样本里——「抽检合格」会给出错误的安全感。等价性路线把错误模式前移成了确定性问题（自等价校验不通过的机器直接拦），人工预算只花在审计任务质量（规格是否完整、测试契约强度）上，而不是逐条核对期望值。另外在规模上：预测路线要求每条任务的期望值都可信，抽检比例下不去；等价性路线在**上千条**任务的量级上直接靠自动校验兜底。

**Q1.5：判分为什么要在新容器里重建，不在写代码的原工作区直接跑？**

A：三个原因。一是**防止判分材料被候选读到**：隐藏测试如果和候选工作区在同一文件系统，模型可以主动读它、针对断言写实现——这是评测无效化的头号漏洞。二是**防「自己给自己打分」**：候选如果能在工作区里放一份自己的测试，判分时被顶掉就彻底失效；我们的做法是判分前清除候选的打包配置与测试目录，把判分测试整树覆盖上去。三是**环境一致性**：评分环境的依赖、路径、Python 版本统一由镜像决定，不取决于候选折腾过什么。

**Q1.6：覆盖率门槛为什么定 0.8？定 0.95 或 0.5 会怎样？**

A：0.8 是「契约强度」与「可达成性」的折中。定到 0.95+ 的问题：能稳定达到这个覆盖率的函数集中在纯计算、结构简单的函数上，长尾（带条件分支多、异常路径多）几乎全部被淘汰——任务集会往「简单函数」严重偏移，区分度反而下降，且闭环轮次成本爆炸。定到 0.5 的问题：大量测试只覆盖了主路径，边界行为（空输入、异常分支）没被断言——这些恰是模型最容易出错的点，任务的**难度区分度**来自边界用例，覆盖率太低等于废掉了区分度。0.8 是这样标出来的：从达标分布的拐点看，0.8 之后再投入轮次，「新增覆盖分支的质量」（是否覆盖可观察行为、是否含异常路径）急降，属于为覆盖率数字而凑断言。

**Q1.7：插桩回填的数据是「真实调用样本」——那随机生成输入（property-based）不行吗？**

A：随机生成对**类型规则简单**的函数可行，对真实业务代码不行：真实调用的输入常带隐式约束（排序过的列表、规范化过的文本、特定分隔符组合），随机生成要么大量违反约束（抛异常）、要么全落在平庸区间（覆盖不到分支）。插桩拿到的是「真实调用长什么样」——包括真实的边界输入（超长文本、混合分隔符）。补充回答另一半：插桩的**可用性边界**也很清楚——函数从未被调用就没有捕获记录，有副作用的函数（写文件、发请求）捕获样本不可复现，要过滤。这两类回落到「仅规格合成」路径，且占比单独统计、不混入主口径，避免「回填收益」被低估或高估。

**Q1.8：任务集怎么做去污染？只查函数名重复吗？**

A：按**仓库维度**切分而不是函数维度。同一仓库的函数之间有强相关性（共享工具函数、相似命名风格），函数级切分会让「同仓库不同函数」分居训练/评测两侧，模型见过仓库的代码风格与工具函数，产生记忆优势。我们的口径是：评测集用到的仓库整体不与训练集重叠；`source_ref`（仓库 + 文件 + commit）随任务落盘，支持任何时间点重做切分。补充一层是公开基准污染：任务库扫描自 GitHub 公开生态，可能撞公开评测集的仓库，训练集按仓库名黑名单过滤后才进 SFT。

### 概念边界辨析

**Q1.9：你说的「等价性测试」和「回归测试」是一回事吗？**

A：不是。**回归测试**的目的是「防止行为变更」——它记录现状（快照式），实现改了、行为变了就亮红；它不关心「现状对不对」。**等价性测试**是对比两个实现的活跃断言——候选与参考在同输入下行为必须一致；它的适用场景是「一个行为两处实现」（重建类任务），而不是「守住一个实现的现状」。落点差异也明显：回归测试追求「尽可能全地锁住现状」（广覆盖、松断言），等价性测试追求「精确对比两边行为」（含异常、边界、类型），松了就没判别力。我们用的是后者。

**Q1.10：「依赖切片」和 RAG 检索代码上下文，是不是一回事？**

A：表面像（都做上下文选择），机制完全不同。RAG 是**语义相似度检索**：按相关性召回片段，保证不了完整性——漏掉一个运行时真正会用到的定义，生成就崩。切片是**静态依赖分析**：保证执行闭包完整（保守但正确），代价是它不认识「语义上相关但运行时无关」的上下文（那部分被排除了，这也正是我们要的降噪）。两者可以组合：切片保证能跑，检索在切片内部做排序（把最可能被引用的定义放前面）——那是我们没做的优化方向。

**Q1.11：「自等价校验」和一般的单测有效性检查有什么区别？**

A：一般单测有效性检查问的是「这个测试能不能测出指定差异」（比如变异测试：给代码注入变异、看测试是否亮红）。自等价校验问的是一个更前置的问题：**「这个测试在已知正确的实现上做得到底对不对」**——它是测试的**自洽性**检查（测试与规范的期望是错位的吗），不是测试的**判别力**检查。两者互补：自等价校验先清掉「期望写错」的测试（我们拦掉 7%），变异式检查再评估剩下的测试有没有判别力（这条我们没做，是已知的改进方向）。

### 失败诊断与排查

**Q1.12：如果某批仓库的任务通过率突然异常高，你怎么排查？**

A：**现象**：某批任务在模型评测上的通过率远超历史水平（比如从三成跳到八成），怀疑判分失效而不是模型变强。**排查**：第一步查判分环境——新容器的测试是否真的在跑（收集期零错误率、平均执行时间与历史分布对比）；第二步查任务材质——这批任务的测试是否全部只断言「形状」（可导入、有属性）而无行为断言，用「断言模式扫描」统计每条测试的断言类型分布；第三步查答案可达性——轨迹/工作区里是否有读取判分材料或参考源码的执行动作（只认工具调用参数字段），以及对目标包上游的获取动作。**根因**：最常见的是两类——判分测试太浅（生成时没上判别式约束），或环境里存在答案可达路径（参考实现在判分镜像里没被隔离）。**解决**：浅测试用「能 fail 掉空骨架」的判别式门槛重生成；可达路径从判分镜像与网络策略双向堵（判分容器不带参考实现源码、出站受限）；两个修复后同批任务重新评一遍，与历史分布对齐后才放行。

**Q1.13：如果判分环境大量出现「收集期报错」，怎么定位和归类？**

A：**现象**：批量任务在「初始化/收集」阶段就报错，测试一条都没跑到——这会系统性把所有模型分数打平，必须先归因再决定弃留。**排查**：把报错按类型分桶——导入失败（缺依赖/包结构错）、数据缺失（测试需要的外部文件不在容器里）、环境冲突（Python 版本、系统库）。我们会在采集侧做一次「重放」：把任务按初始状态重建后跑一遍参考实现，参考实现都过不了的就判环境问题。**根因**：三个主要来源——种子筛选时的「重依赖在 import 时被真实触达」（这类库的判分环境根本装不起来）、测试依赖的外部资产（数据文件、网络）没被纳入镜像、有状态函数的初始化必须按特定顺序执行。**解决**：环境问题分三类处理——装不动的库降级或弃用（种子里就标注）、外部资产在镜像构建期预置、状态顺序用手写 fixture 固化；处理不了的进 pending 池，不进入判分统计分母。

**Q1.14：闭环跑完覆盖率还是上不去，怎么分析？**

A：**现象**：三轮闭环后一批函数的覆盖率仍在 0.8 以下，任务产出率低于预期。**排查**：先看失败函数的分支结构——把未覆盖分支归类：异常处理分支（需要特定失败输入）、防御性分支（需要畸形数据）、平台分支（需要不同 OS/版本）、并发/时序分支（不可稳定复现）。再对照生成的测试输入来源——随机猜测的输入几乎不可能命中前两类中的具体条件。**根因**：覆盖率上不去的核心是**输入构造能力不足**，不是测试写得不好——异常分支需要「能让函数出错的输入」，而模型凭直觉构造的输入太温和；并发/平台分支属于本质上难测的类别。**解决**：对可测的两类（异常、防御分支）加真实调用样本的回填（真实场景里出现过错误输入）、在覆盖率提示里显式标出「异常分支」类型并给提示；对不可测的类别（并发/平台）调整统计口径——从覆盖率门槛里豁免，避免为了数字写假测试。这轮调整后达标率才有第二轮 45% → 87% 的曲线。

### 量化速查

**Q1.15：数据规模多少？留存比例呢？**

A：种子侧 **210 余个**仓库（中高热度、可浅克隆），抽取约 **4.6 万个函数**；经自等价校验、双门槛闭环、去污染过滤后产出 **1.4 万条**任务，整体留存约三成。损耗大头两类：难测函数（依赖外部状态、无稳定输入）与缺陷测试拦截（约 7% 的自等价校验失败率）。评测侧与训练侧按仓库维度切分。

**Q1.16：上下文缩短和通过率提升的具体数字？怎么测的？**

A：同一批函数在两种上下文供给（整仓 vs 3 层切片）下各跑一遍对照：上下文平均长度**降低约 60%**，测试合成的一次执行**通过率提升约 14pp**（工程实测口径）。「一次执行通过率」= 生成后首次进沙箱就不报错、且断言可执行的比例——它同时受上下文质量（引用正确）与测试质量影响。

**Q1.17：一条任务的数据长什么样？给我把字段说清楚。**

A：七个字段：`task_id`（仓库缩写-函数名-序号）、`signature`（Python 类型注解完整保留）、`spec`（3–8 句自然语言规格，含 1–2 个输入输出示例与异常契约）、`source_ref`（仓库 + 文件 + commit，供溯源与去污染）、`test_source`（1–3 个判分测试，对模型隐藏）、`coverage`（判分测试在参考实现上的分支覆盖率，入库门槛 ≥0.8）、`verdict`（自等价校验结果）。给一条具体样例：`spec` 写「把 text 按 sep 切分并保留空字段；`split_fields("a,,b", ",")` 返回 `["a", "", "b"]`；sep 为空串时抛 ValueError、消息为 `separator must not be empty`」，对应判分测试断言这两条行为——下游模型只看前两列（签名 + 规格）写实现。

**Q1.18：判分一批任务要多久？用什么资源？**

A：判分在 CPU 集群的容器里跑：**32 并发容器**、单例超时 600 秒，一批（万条量级）约 **4 小时**。测试与规格合成环节用 **8×H100** 做推理、约 **6 小时/批**（1 万条任务、temperature 0.7、单条最多 3 次尝试）。抽取与切片是确定性代码，64 并行进程、约 **2 小时/批**（1 万个函数）。闭环重生成每轮约 **3 小时**。

## 二、项目二：长程代码 Agent 轨迹的质量审计与增强训练

### 开场概览

**Q2.1：用三句话讲清这个项目——处理什么数据、产出什么、核心难点？**

A：处理的是一批长程编码任务的 Agent 轨迹——单条任务百轮量级工具交互、数万 token，总规模 **2,700 余条**。产出有三样：经过质量门筛选的干净训练集、两类增强样本（关键决策点注入版、压缩恢复版）、以及一套可复用的轨迹治理链路。核心难点：一是**低质轨迹会教出坏行为**（连续编辑不回读验证、宣告完成但从未执行验证），需要在训练前系统性识别；二是**长轨迹的上下文结构特殊**（运行框架会触发压缩，模型在压缩后的行为模式与常态不同），训练数据要覆盖这种形态；三是**效果评估容易失真**（得分变化混着「答案获取红利」等非能力因素，必须分账才能读出真实信号）。

**Q2.2：这个项目和项目一是什么关系？**

A：同一条数据链路的前后两段。项目一解决「任务供给」——造出带可靠判分的函数级任务，判分口径（行为等价、自等价校验）保证了「任务可验证」这个前提。项目二解决「轨迹质量」——任务被 Agent 真实执行后产生长轨迹，这些轨迹是训练 SFT/RL 的原料，但采集成品需要治理：静态预筛把坏形态挡在门外、归因体系给低分任务定位病灶、增强环节把成功轨迹改造成更高质量的训练样本、蒸馏后按口径分账评估。一句话：项目一保证「题可靠」，项目二保证「答干净」。

**Q2.3：你负责哪些模块？**

A：我负责**过程监督注入**与**压缩恢复样本合成**两个模块的设计与实现——前者是触发点路由、采样预算、注入文本与回填不变量的全套实现；后者是切点检测（含顺延逻辑）、N+1 段样本构造与摘要消息对的合成。另外参与了静态预筛指标（盲写指标）的口径统一与流程接入、失败模式归因到打包环节的接入，以及蒸馏对照的评测口径与分账统计。

### 递进追问链

**【追问链 1：过程监督注入】**

**L1（是什么）：「过程监督注入」具体注入了什么、注入到哪？**

A：往成功轨迹的**关键决策点**注入一段「状态感知」思考片段——内容只描述「已经做了什么、处在任务的哪个位置、还差什么」，不做操作指导。触发点有九类：完成宣告点（必采）、报错到修复的拐点、官方测试执行点、任务阶段边界、任务分解完成后首开工、盲写段首尾、token 突增点（fallback）、重读密集点（fallback）。注入方式是在该轮 assistant 消息的 `content` 前面拼接这段思考，**只改 content、不触碰工具调用字段**——保证 `tool_calls` 与后续 `tool` 结果的配对结构不变。单条轨迹平均注入 **3–4 个**点。

**L2（为什么）：为什么不注入「你该去验证一下」这种操作指导？**

A：两个原因。一是操作指导在数据里会变成「被喂的规则」，模型学到的是「等提示再行动」，而不是「自己形成状态判断」——我们要教的是**任务状态感知**（知道自己做完了什么、还差什么），而不是「验证」这个单动作。二是操作指导与具体工具的耦合太强：写「去跑 pytest」在换 harness、换工具集的部署里就是错的；而「回顾已完成部分与待办差距」这种状态感知是跨工具集通用的。这也解释了注入的观察点为什么选在「完成宣告」「修复拐点」——这些位置天然要求模型做状态判断，注入在这里教的是「判断方式」，不是「动作指令」。

**L3（怎么做）：采样预算怎么算？为什么必采点不限流？**

A：预算用调和平均式公式分配：`base = max(1, (n_cand * MAX_SAMPLES) // (n_cand + MAX_SAMPLES))`，`n_cand` 是去掉头尾的候选轮数，`MAX_SAMPLES` 取 10 上下；上下文特别长的轨迹再加权（>100K 字符 +2、>50K 字符 +1）。候选点按间隔均分（`gap = max(2, n_cand // (eff_max + 1))`），避免注入点扎堆在轨迹某一段。必采点（完成宣告）**不受限流影响、一定被采**——它是整条轨迹里最该被核对的位置：模型在这里说「我完成了」，而验证幻觉（自我宣告完成、其实从未执行过任何验证）恰好是这条链路上最危险的失败形态；漏掉这个点等于放过对它的唯一干预入口。

**L4（failure mode）：注入跑挂过吗？怎么处理的？**

A：有过三种。其一，**注入文本被模型学成「标签复述」**：早期版本给注入片段加结构化标注（「阶段：实现中」），训练后发现模型在对应场景复述标签、不产生状态判断——解析上是「注入了什么格式，模型学什么格式」，改成自然口吻（英文、直接说事）后对齐。其二，**回填截断**：从截断导出版本回填时丢了触发点之后的内容，注入片段跟轨迹对不上——修法是回填统一从完整轨迹存档恢复。其三，**质量门误伤**：注入片段过短、或没覆盖到「核对」语义的，会污染数据——用纯关键词判据（长度 + 目标词组 + 结论词组，零 LLM 调用）过滤，不达标就丢弃该注入点。

**L5（边界/未做）：这个模块的局限是什么？**

A：三条。一是**只做「成功轨迹」的增强**——失败轨迹的修复样本走的是另一条线，两条线的风格统一没有系统化。二是**触发点表是先验设计**，没有用评测端的失败模式统计反向校准优先级（比如某类 bad pattern 高频出现，对应触发点就该加权）——这是明确的改进方向。三是**注入质量门是关键词级**，能筛掉「明显垃圾」，筛不出「看着对但对不到点上」（比如完成核对没有引用任何具体待办项）——升级方向是结构判据（核对必须引用至少一个具体项、规划与后续真实动作窗口一致）。

**【追问链 2：压缩恢复样本合成】**

**L1（是什么）：压缩恢复样本是怎么合成出来的？**

A：把完整长轨迹按「上下文压缩边界」切开、重建成多条独立训练样本的过程。具体是：逐轮累积 token 估算，达阈值（**5 万 token** 量级）后寻找切点——不是到达即切，而是**顺延**到第一个「重锚点」轮之后；切点前的部分原样成一条样本（压缩前形态），切点之后的部分重建成「任务前缀 + 摘要消息对 + 尾部」的样本（压缩后形态）。一条长轨迹因此切出 N+1 条独立样本。一批轨迹切出 **130 余段**，工具调用配对零孤儿。

**L2（为什么）：为什么切点必须顺延到「重读或执行测试」的轮次？**

A：这是一个**训练信号方向性**的设计。原轨迹在压缩点之后的动作，天然是「先重读文件/先跑测试」——这是「压缩后如何恢复」的正确反射。如果我们不判定位置、随手在任意轮切分，切点后第一个动作很可能是「继续写代码」——重建样本就会把「压缩后凭记忆接着盲写」这个**错误模式**当成示范写进训练数据，方向完全反了。所以规则是：达到 token 阈值后标记「待切」，往后找到第一个满足条件的轮（该轮工具调用含 Read 或 pytest 类命令）且尾部还剩 ≥4 轮才执行切分。宁可多等几轮，不可切错位置。

**L3（怎么做）：摘要消息对具体包含什么？有什么质量门？**

A：摘要消息对是对齐主流编码 Agent 压缩后消息形态的两条消息：先是两条系统提醒（最后一次 Read 的输入与结果、超长截断），然后是 CONTINUED_PREFIX 开头的**九段有损摘要**——主要诉求、关键技术概念、涉及文件与代码段、错误与修复记录、问题解决过程、用户消息记录、待办任务、当前工作、下一步，最后是恢复指令（「直接继续，不要复述摘要」式的引导）。质量门有两道：长度与**核验语义词**检查（摘要或引导里必须出现确认、验证、检查、重读、改前先读、跑测试这类词——保证恢复行为是「先验证」）；**禁词**检查——摘要与引导里不得出现「压缩」「摘要」「上下文上限」这类元叙述词。禁词这条来自一个明确的教训：推理时运行框架的指令是「不要复述摘要」，训练数据里如果注入「我刚被压缩过」的元信息，会造成训练与推理的口径不一致——模型会把「意识到自己是被压缩的」当成行动前提。

**L4（failure mode）：切分环节出过什么问题？**

A：核心关注点是**结构不变量**：切点必须落在轮边界上（不能把一次 assistant 消息和它的工具结果切开），否则两段样本里都会出现「孤儿的工具结果」——训练侧直接报错、样本整条报废。实现里切点只取轮边界、切分后逐段校验配对（`tool_calls[].id` 与 `tool_call_id` 一一对应）——一批 130 余段全部通过。另一个问题是**摘要过信度**：早期摘要模板没有把「当前正在验证的假设」单列，压缩后模型重建状态时经常重新论证已经验证过的结论——后来在摘要结构里固化了「当前工作」字段，并把它与「待办任务」分开写。

**L5（边界/未做）：这模块还有哪些没做的事？**

A：两件。一是**切密程度的标定**：我们把切分阈值刻意设得比真实压缩触发点更密（为了多产样本），但没有系统对照过「训练时的压缩形态与推理时的真实压缩形态」的分布差异——按真实触发时机切的对照组是应该补的（如果两者分布差太远，模型可能在错的形态上学习）。二是**压缩与恢复的策略联动**：训练数据教「恢复行为」，推理侧框架的压缩策略（保多少、什么时候压）是另一个可优化对象——目前两条线是各自独立的，把「压缩策略」与「恢复样本训练」做成联动闭环是更远的计划。

**【追问链 3：盲写指标】**

**L1（是什么）：盲写指标怎么定义、怎么算？**

A：定义是「连续写、改操作之间无任何验证调用的最大次数」。计算是单遍扫描：遍历轨迹消息里的工具调用，连续的 Write/Edit 累加，遇到 Bash 类验证调用归零，取最大值。口径上最关键的是「什么算验证」——执行测试、跑命令、甚至 import 冒烟都算；纯读文件不算（读不是验证，读完不跑也不构成行为验证）。

**L2（为什么）：为什么这个简单指标有判别力？**

A：因为它直接对应一条**因果链**：连续写大量文件不回读、不运行 → 代码结构或导入关系真的坏了也发现不了（自测本身也是盲写的产物，测不出来）→ 判分环境执行时在「收集期」就直接报错。我们对分布做过统计：判分通过的轨迹，该指标中位数在 **15** 上下；判分失败、且在收集期就报错的轨迹，中位数在 **31** 上下（两倍差距），极端个例接近 90（两百多条消息里 60 多次写改操作、30 多次编辑——全程没验证过一次）。区分度强于最终得分本身，这是它能当质量门的原因。

**L3（怎么做）：为什么一个指标要复用到三个地方？**

A：因为它「零成本可算、区分度强」，而这三点上的复用的收益各不相同：**SFT 静态质量门**（超阈值进修复队列，防坏样本进训练集，是防守）；**rollout 运行时节流**（采集时运行期监测，超阈值在下一轮前插入「先做冒烟验证」的提醒——把治理从「事后过滤」前移到「运行中纠正」，是纠偏）；**失败预测特征**（预测「这条大概率要失败」，用于资源调度如优先重投，是调度）。三处共用同一计算口径（同一段扫描代码），保证「质量门拦掉的」和「节流提醒的」是同一批形态，不出现两套标准打架。

**L4（边界/未做）：这个指标的局限？**

A：它是**时序形态特征**，不是「质量」的完整刻画——它抓「写了不验证」，抓不到「验证了但验证得不对」（比如自测全绿但与判分契约错位——这属于另一类失败模式，靠归因体系的其他维度覆盖），也抓不到「没写多少但想了很久」的合理形态。另外阈值的选取（20 上下）是分布拐点定的，对**不同任务形态**（有的任务天然要连续生成多个文件）会有误伤——我们的缓解是把它放进五维评分卡的权重体系里（占约一成），不单独一票否决（只有答案获取是一票否决）。

### 设计决策与取舍

**Q2.4：为什么把治理做进「训练样本」而不是只做「过滤」？直接扔掉坏轨迹不就行了？**

A：过滤只能保住「下限」，増强才能提升「上限」。垃圾轨迹直接扔当然对，但这条链路的真实约束是：**成功轨迹的采集成本极高**（长任务单条要跑百轮工具交互，一条轨迹的采集成本远超短任务），纯粹过滤会让「可用样本」永远停留在采集到的自然质量水平上。增强环节做的两件事都不增加采集成本、只增加加工成本：过程监督注入把「成功过程」变成「带状态判断的成功过程」（教过程性判断）；压缩样本合成把「一条长样本」变成「N+1 条覆盖不同上下文形态的样本」（教压缩恢复）。另外，过滤做不到「反向样本构造」——失败轨迹修复后来产出的样本（偏好对与修复段）这种正负对比的素材，只有靠加工产出。

**Q2.5：五维评分卡为什么是加权分而不是「全部通过才入库」的硬门？**

A：硬门会让通过率塌缩。五个维度里有强项弱项的组合很常见（比如判分通过率高但盲写偏高、或完成标记缺失但其余全好）——硬门把它们全部拒掉，留存率会跌到不可用的水平，而且**误拒的样本质量其实比误收的低质样本更好**（拒绝标准差那一档的成本更高）。加权分的意义是**把样本分到三个去向**（直接入库 / 修复队列 / 重采丢弃），每一档都是「资源匹配质量」：高分样本直接进训练；中档样本给一次修复机会（定向重采样），修复成本低于重采；低分样本快速丢弃。唯一的一票否决是**答案获取**——它不参与加权，命中即出局，因为它的危害是「教模型走捷径」，与质量分数不能互补。

**Q2.6：分账归因听起来是「报表技巧」——为什么值得当成一个技术设计点？**

A：它不是报表技巧，是**训练信号有效性**的判定方法。抽象地说：一次训练运行后的总分变化是多个来源的叠加——真实能力变化、行为风格变化（更主动/更保守）、以及非能力因素（答案获取行为被消除、评测污染）。不拆开，三种情况会被报成同一句话「训练有效/无效」：我们实际遇到的例子——某次对照总分掉了十几分，看起来像训练失败；分账后看到退步的约**七成**集中在「训练前依赖答案获取拿到虚高」的那批任务上（训练后模型不再走捷径、分数回到真实水平），其余任务基本没动。这是**正面结论被误读成负面**。另一个例子反过来：另一次表观增益约六成来自残留的答案获取行为——如果不分账，会把「作弊红利的回流」当成训练收益。所以分账不是美化报告，而是决定「这批数据要不要发、下一轮加什么数据」的判断依据。

**Q2.7：增强数据训练的总分没动——这个结果怎么解读？它到底有没有用？**

A：要分两层看。**第一层（得分）**：总分差异处于噪声量级（单 trial、|Δ|<0.05 会降档表述为「趋势性」而非「确证性」）——不能声称增益。**第二层（行为指标）**：同样的模型在轨迹行为上实质改善——盲改次数 **−38%**、接口签名错位 **−62%**、最长盲改从 8 轮上下压到 **4 轮**上下、工具报错减半。这两个结论并不矛盾：行为指标衡量「过程质量」，得分衡量「结果成功率」，过程质量改善而成功率未变，说明当前的提升被其他瓶颈（任务难度、探索预算）掩盖——在这种情况下正确的动作是**保留行为改善、继续定位成功率瓶颈**（比如做行为指标与最终得分的相关性分析，确认哪些行为改造最可能转化为得分）。这也直接总结成我们的报告纪律：行为指标与得分分开报告，两类结论各自标注效力等级。

### 概念边界辨析

**Q2.8：过程监督注入和 PRM（过程奖励模型）有什么区别？不都是在「过程」上做事吗？**

A：目标相反、作用路径相反。**PRM** 是训练时给「中间步骤」打分（学习一个能评估步骤质量的模型，把它的分数掺进 RL 的奖励或做候选排序）——它作用于**优化目标**，是「在训练中加过程信号」。**过程监督注入**是把「状态感知的思考」写进训练数据本身——它改变的是**数据形态**，模型按常规 SFT 学「在这个位置应该产生什么样的状态判断」。结果上的差别：PRM 需要额外的模型与奖励工程（还会引入 PRM 被 hack 的风险），注入只改数据、零推理成本；PRM 教「哪种步骤得分高」，注入教「怎么做状态判断」。两者不互斥，但落点、成本与失效模式完全不同。

**Q2.9：压缩恢复样本合成和常见的「上下文压缩策略」是不是一个东西？**

A：不是，**一边训练、一边推理**。上下文压缩策略是**推理侧**的运行时行为：框架把旧对话折叠成摘要、保最近若干轮，目标是在窗口限制下维持推理继续（我们项目里也接触过对照实验，比如工具返回内容按类型裁剪）。压缩恢复样本合成是**数据侧**的加工：把压缩这个「已经会发生的事实」变成训练形态——教模型在「只剩摘要 + 最近几轮」的上下文下怎么恢复工作状态。换句话说：压缩策略解决「压缩怎么做得更好」，恢复样本解决「模型被压缩后怎么行为正确」。这两个的东西经常被混为一谈，但一个是系统优化、一个是训练数据设计。

**Q2.10：为什么不直接用「轨迹长度/步数」当质量指标？盲写指标强在哪？**

A：轨迹长度是「工作量」，不是「质量」——长轨迹既可能是深度探索（好），也可能是盲目试错（坏）；步数与成功率的关系在数据里是弱相关且非单调。盲写指标强在它**指向一个具体机制**而不是规模：连续写改不回读验证，是「操作冲动压过验证纪律」的直接行为特征，因果链末端（收集期失败）是确定的。此外它的计算成本是单遍扫描（零 LLM、零容器），可以在一整批上全量跑，而「用长度判断质量」还需要按任务难度的归一化（长任务天然长），引入额外的口径复杂度。

### 失败诊断与排查

**Q2.11：增强数据训练后总分没动，你怎么确认增强没白做？**

A：**现象**：两版数据（初版 vs 增强版）在同集对照训练后总分差在噪声内。**排查**：第一步先验证训练本身没跑歪（loss 曲线、KL、gradient norm 与初版同分布）；第二步把评估换成「行为指标剖面」——在留出集上统计盲改次数、接口签名错位率、工具报错率、超轮次比例等过程指标（这些指标不依赖任务是否解出，粒度更细）；第三步做**逐样本对照**：同一批题目上两版本各自的行为差异是否成系统（比如增强版在「连续编辑段」显著更短）。**根因**：行为改善真实发生但未转化为成功率——瓶颈在任务难度与探索预算（长程任务的最终成功率由任务本身的解法收敛性主导，行为规范只影响「不犯错」的下限）；也可能增强数据占比太小（比如只占训练集两成），信号被稀释。**解决**：把行为指标写入常规评估报告（不再只看总分）；对增强样本做配比扫描（占比 2-4 成间找增益拐点）；同时确认瓶颈假设（若任务难度主导，则需要数据侧补「有梯度」的任务）。

**Q2.12：如果发现模型学会了「复述注入的思考格式」而不是形成状态判断，怎么发现、怎么处理？**

A：**现象**：抽样评估时模型在相似场景输出格式一致但内容空洞的「自检」段落（只提「检查一下」不引用任何具体待办项）；更隐蔽的信号是评测的行为指标没有任何改善（如果注入真的教了状态判断，最长盲改、验证前置率这些指标应该动）。**排查**：把「注入文本的风格」与「模型输出片段」做分布对照——检查模型输出是否在模仿注入的结构特征（比如格式、句首词组），而非内容；再做一个消融（用自然口吻模板 vs 结构化模板各训一版，比较行为指标）。**根因**：训练数据里的注入文本与模型该学的东西错位——如果注入文本本身是「格式性」的（有标签、有固定模版），模型的梯度就沿着「复述格式」走；同责的还有质量门漏放（没有具体内容的注入点没被拦住）。**解决**：注入文本全部改用自然口吻（写思考、不给结构）；质量门从关键词升级为结构判据（核对类注入必须引用至少一个具体待办项或失败点）；重新生成注入版数据后重训对照。

**Q2.13：训练中出现 KL 快速上升伴随行为退化（工具调用循环重复），怎么排查？**

A：**现象**：蒸馏训练中整体 KL 爬升，评测里出现「同一条命令重复调用」「先读后读反复横跳」这类低效行为，成功率同期下滑。**排查**：先区分是「策略漂移」还是「数据形态冲突」——看 KL 尖峰与哪类训练样本在时间上对齐（按样本类别分桶看 loss/KL 贡献）；再检查数据侧是否有长轨迹样本超过序列上限被截断（截断样本会教出「上下文丢了一半还要继续」的行为，类似重复读文件）；另外核对「蒸馏版与原始版的数据配比」（增强样本占比过高时，模型可能在压缩形态上过拟合、在常态上下文上退化——两种情况的行为特征混淆）。**根因**：最常见是两类——样本截断引入了「残缺上下文继续作业」的坏模式；或增强样本的分布与常规推理分布不一致（比如压缩样本占比过大，模型对「摘要后状态」过度自信）。**解决**：对超长样本做长度过滤或分段（保证不丢关键段），调整数据配比（压缩样本单列重扫占比），并在训练中加入格式与重复度的过程监控指标（把它作为训练期告警，而不是只在评测时看）。

**Q2.14：训练奖励一直涨，但留出集评测不涨，你怎么走？**

A：**现象**：训练侧 reward 曲线稳定爬升，held-out 成功率停滞、甚至下滑。**排查**：第一步先查「奖励是否被可乘之机套利」——抽最高奖励批次的轨迹人工看过程，重点检查「奖励模态之外的动作」（长文本套话、重复工具调用、捷径行为），这一步用「奖励与行为帮助度的倒挂」判断（高奖励轨迹的实际任务进度）；第二步做**答案获取分账**——把评测任务按「训练前是否依赖捷径」分组看变化（如果训练前靠答案获取拿高分的任务在训练后崩掉、其余任务没动，那说明训练在消除捷径、真实能力未提升）；第三步查评测口径（评测 harness 与训练 harness 是否一致——协议不一致会把退化误计为「没涨」）。**根因**：三类——奖励被套利（reward 与真实进度脱钩）、评测污染（数据泄漏让训练前基线虚高，掩盖真实提升）、训练与评测不一致（格式/协议差异制造系统性扣分）。**解决**：奖励套利用「过程检查 + 奖励设计」修（把过程质量纳入奖励或不达标的动作直接归零）；评测污染靠训练集黑名单去污；协议一致性用「同一 harness 跑训练与评测」并通过解析失败率监控（我们的同类改造把解析失败率从 6.1% 压到 1.3%）。

### 量化速查

**Q2.15：这批轨迹的规模和长度分布？**

A：治理了 **2,700 余条**长程轨迹；单任务百轮量级工具交互、数万 token。配套的增强产出：过程监督版平均每轨迹 **3–4 个**注入点；压缩恢复版一批切出 **130 余段**独立样本（配对零孤儿）。

**Q2.16：盲写指标的分布，再说一下具体数字。**

A：判分通过的轨迹中位数 **15**，判分失败且在收集期报错的 **31**，极端个例接近 **90**。质量门阈值取 **20** 上下（分布拐点）；五维评分卡里该维度权重约一成。同一指标三处复用：SFT 质量门（超阈进修复队列）、rollout 运行节流（超阈插验证提醒）、失败预测（资源调度）。

**Q2.17：一条轨迹样本的数据长什么样？**

A：字段：`task`（任务指令，数千 token，含规格与约束）、`messages`（system/user/assistant（含 tool_calls）/tool 交替的百轮序列）、`tools`（8–12 个工具的声明清单）、`meta.resolved`（判分是否通过）、`meta.hidden_pass_rate`（隐藏测试通过率）、`meta.max_blind`（盲写指标）、`meta.injections`（注入点列表，如 `[{turn: 37, type: "completion_check"}]`）、`meta.segment`（压缩段标记，如 `{"part": "B", "of": 3, "cut_token": 52000}`）。一条具体形态：第 12 轮模型说「先读入口文件确认包结构」并调用 Read；第 38–39 轮连续两次 Write 补模块（无验证）；第 61 轮说「所有测试都通过了」——而它的工具调用从来没有执行过 pytest（这就是完成宣告点的注入对象：在它宣告的位置注入一段「核对：验证依据是什么」的思考）。元数据里这条大概率是 `resolved: false`、`max_blind: 31`。

**Q2.18：蒸馏阶段的资源和配置？**

A：蒸馏 SFT 在 **16×H100** 上跑、约 **12 小时**（30B 级学生模型、lr 1e-5 cosine、2 个 epoch、序列上限 128K）。注入标注与判分推理用 **8×H100**、约 **5 小时/批**（千条轨迹）。压缩切分与打标是 CPU 处理：约 **2 小时/批**；轨迹导出与预筛约 **1 小时/批**（千条轨迹、32 并发）。

## 三、跨项目串联与全局理解

**Q3.1：两个项目合起来，整条数据链路的闭环是什么？**

A：`真实仓库 → 函数抽取/切片 → 任务合成（含判分测试）→ 沙箱判分与覆盖率筛选 → 任务池 → Agent 执行采集轨迹 → 静态预筛（盲写指标）→ 失败模式归因 → 训练样本增强（过程监督注入 + 压缩恢复合成）→ 蒸馏训练 → 分账评估 → 反馈到数据配比调整`。两个项目各占半段：项目的判分协议是「任务可验证」的底座（自等价校验在入库前拦缺陷测试）；轨迹治理是「答案干净」的保证（答案获取一票否决、低质形态过滤）。闭环的反馈点在于：分账评估得出的「哪些任务有梯度、哪些行为在改善」，决定下一批任务合成与增强的配比。

**Q3.2：项目一的判分体系对项目二有什么直接影响？**

A：影响是结构性的。项目二的「质量审计」要信得过，前提是**判分信号本身可信**——项目一的自等价校验（先在参考实现上跑测试、拦掉缺陷测试约 7%）和容器化判分（不读候选实现、判分材料隔离）保证了「通过/失败」这个信号不是噪声；否则归因体系会把「判分错误」归成「模型能力问题」。反过来，项目二的归因结论反哺任务侧：像「验证模式错位」（自测与判分契约不一致）这种高频失败模式，能定位出任务规格是否表达不足——如果规格没把异常契约写清楚，模型自测与判分测试的错位就是任务本身的问题，而不是模型的问题。这两侧的联动是我们实际用到的数据质量闭环。

**Q3.3：如果让你从零重做整条链路，最大的设计变更是什么？**

A：把「质量治理」前置成「生成约束」。现在是「先生成（任务/轨迹）→ 再审计 → 再增强」的流水线，审计发现的问题（验证模式错位、盲写）如果能在生成端就抑制，整条链路的成本会大不一样——比如任务合成时强制「规格必须含异常契约与边界示例」（现在的部分任务规格偏粗）、轨迹采集时在运行期做更强的验证节流（现在只做了监测提醒）。另外我会更早做「行为指标与得分相关性」的分析——先用小批量数据摸清「哪些过程行为真的与成功率相关」，再决定增强环节投在哪些行为上；而不是先做增强、再看行为指标动没动。一句话：从「先造后滤」转向「边造边校」。

**Q3.4：你负责的模块如果出问题，对上下游的影响是什么？怎么降级？**

A：以等价性判分为例——如果判分协议出问题（比如自等价校验失效、测试缺陷漏放），影响是全线性的：任务池质量不可信 → 训练数据带噪声 → 评测分数失真。**降级方案三层**：入库端加强抽检（对 `verdict` 通过的测试按比例人工复核，成本可预算）；任务侧保留来源元数据（`source_ref`），可以按仓库维度快速定位与召回「问题批次」；评测端用「仅保留通过双门槛 + 自等价状态为 passed」的严格子集出分，与全量出分并列报告——严格子集与全量差异过大时暂停使用全量口径。轨迹侧的降级同理：质量门、预筛、增强三步各自可独立关闭，回到「原始轨迹 + 基础过滤」的下限形态。

**Q3.5：面试官问：「你这个从真实仓库造任务再做轨迹治理的项目，跟 SWE-bench 修 bug 的数据链路，不就是一回事吗？」**

A：不是一回事，任务形态与判分依据都不同。**任务形态**：SWE-bench 式任务是「给定仓库 + issue，修复缺陷」，输入带明确的变更意图；我们从零重建类任务是「给定规格，实现函数/库」，输入是行为规格、没有变更对象。**判分依据**：修 bug 类用测试翻转（目标用例从 fail 到 pass、防回归用例保持 pass），天然有「变更前后」对照；重建类用行为等价（候选与参考同输入同输出）、加自等价校验保证测试可信。**难点分布**：修 bug 类的难点在定位（在真实仓库里找到缺陷位置）；重建类的难点在长程的规格实现与结构落地（从零建立包结构、对齐契约）。两者的数据治理有共用的方法论（质量门、分账、去污染），但拿一个去套另一个，判分协议和失败模式都会对不上——这也是我两个项目都以「判分可信」为设计中心的原因。

**Q3.6：面试官追问：「那你这个任务集评测出来的分数，凭什么说它反映模型真实能力？」**

A：四个保障。**判分可信**：行为等价 + 自等价校验 + 判分材料隔离（隐藏测试不进候选工作区、容器重建执行）。**去污染**：评测集与训练集按仓库维度切分（同仓库任务强相关，函数级切分会给记忆优势）；训练数据按仓库黑名单过滤。**难度分层**：任务带难度信号（判分达标分布、盲写形态统计），评测报告按难度分档，避免「任务难度偏移」被读成「能力变化」。**口径一致**：评测的 harness 与训练一致（协议差异会制造系统性扣分，这一类误差最容易被误读为能力下降）。同时要诚实地说边界：分数只在「行为复现类任务」上有解释力，且单一分数不解释「为什么」——解释力来自我们配套的失败归因（哪类行为在失败里占主导），这也是失败模式归因体系真正值钱的地方。
