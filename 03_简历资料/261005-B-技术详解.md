> **🎯 项目整体话术**：项目一为编程 Agent 的评测与短程训练供给函数级编程任务。做法是从 210 余个开源 Python 仓库抽取约 4.6 万个函数，为每个函数合成判分测试与自然语言规格，最终入库 1.4 万条逐条经沙箱验证的任务，形态为对模型暴露签名与规格、判分测试隐藏。判分不依赖模型预测的期望值，只断言候选实现与参考实现在同一组输入下行为一致；合成上下文不提供整个仓库，只提供依赖切片得到的执行闭包。测试一次执行通过率由朴素流程的 58% 提升至 74%，覆盖率达标率经三轮反馈由 45% 提升至 87%。本人负责等价性判分与依赖切片两个模块的设计与实现，参与插桩采集与多轮反馈生成的实现。

### 1.1 参考实现作 oracle 的等价性判分

> **🗣️ 话术——参考实现作 oracle 的等价性判分**：由模型预测期望输出的测试，在非平凡函数上经常写错期望值，错误的期望值入库后，正确实现被判错，错误实现可能被判对。方案为测试不写字面期望值，只断言候选实现与参考实现在同一组输入下的返回值、异常类型与异常消息一致，原函数即标准答案。每条新测试入库前先在参考实现上执行一遍，执行失败即判为测试自身缺陷并拦截，拦截约 7%。判分在新建的隔离容器中执行，执行前删除候选工作区里的测试目录与打包配置，只回收逐测试的通过结果。同批 800 个函数对照，预测期望值写法的抽检缺陷率为 28%，等价性断言写法为 1.9%，测试一次执行通过率由 58% 提升至 72%。

**动机**：函数级任务的判分测试由模型合成，最直接的写法是让模型写出「输入与期望输出」对。期望输出需要模型在脑中执行一遍函数，对 `Decimal` 舍入、空字段保留、生成器惰性求值这类细节，模型的预测经常出错。同批 800 个函数的抽检中，预测期望值写法有 28% 的测试存在缺陷，其中多数是期望值本身写错。缺陷测试带来两个方向的误判：正确实现被判为失败（假阴），错误实现恰好与错误期望一致而被判为通过（假阳）。这些误判会随任务进入评测与训练，在评测侧表现为分数噪声，在训练侧表现为错误的监督或错误的 reward。问题落在判分协议这一环，是因为期望值的来源决定了判分能否被核查；只要期望值由模型预测，就没有独立的依据去检验它。

**做法**：
1. 测试形态改为对照执行。判分时把候选实现与参考实现加载进同一执行环境，测试对同一组输入分别调用两边并比较结果：返回值直接比较；浮点数按相对误差 1e-9 比较；不可直接比较的对象比较序列化结果；异常路径比较异常类型与消息，规格允许时按子串匹配。测试代码中不出现字面期望值。
2. 自等价校验。每条新测试先以参考实现同时充当候选与参考执行一遍。理论上这一步必然通过；未通过说明测试自身有缺陷，例如调用了不存在的 API、构造的输入不满足前置条件、依赖缺失或断言写反，此时标记 `test_defect` 并拦截，不进入后续流程。
3. 隔离容器判分。每次判分新建容器，先删除候选工作区中的 `tests/` 目录与 `pyproject.toml`、`pytest.ini` 等配置，再写入隐藏测试，用固定的 `PYTHONPATH` 执行，只回收逐测试的 pass 或 fail，不读取候选源码。容器初始化阶段的 `SyntaxWarning` 一类环境噪声单列状态，不计入判分分母。
4. 数值演算。以一批 1 万条新测试为例：自等价校验拦截约 7%，即 10,000 × 7% = 700 条在入库前被剔除；若沿用预测期望值写法，按 28% 的缺陷率估算，10,000 × 28% = 2,800 条缺陷测试需要人工抽检才能发现。两种写法在同批 800 个函数上的对照为：一次执行通过率 58% 对 72%，抽检缺陷率 28% 对 1.9%，缺陷绝对数由 800 × 28% = 224 条降到 800 × 1.9% ≈ 15 条。

**取值依据**：关键参数是自等价校验的执行次数与浮点比较容差。自等价校验只执行一次：对确定性函数，一次执行即可暴露测试缺陷；对含随机性或依赖时间的函数，曾试过连续执行 3 次并要求结果一致，额外拦截的比例不到 0.5%，且判分成本增加约两倍，因此改为在抽取阶段直接剔除依赖随机种子与系统时间的函数。浮点容差取相对误差 1e-9：取 1e-12 时，同一函数在不同 BLAS 实现下的结果被判为不一致，误判约 1.3%；取 1e-6 时，部分数值算法的错误实现（如少一次迭代）被判为等价。

**收益**：同批 800 个函数对照，测试一次执行通过率由 58% 提升至 72%（+14pp），抽检缺陷率由 28% 降至 1.9%；自等价校验在入库前拦截约 7% 的测试缺陷。人工抽检从「检查每个期望值是否正确」变为「检查测试是否覆盖了规格中的行为」，抽检的工作量与判断难度都明显降低。

**适用边界与代价**：等价性判分以参考实现可信为前提，参考实现自身的 bug 会被当成标准行为保留下来；对这一点的处理是在规格提炼时以已通过测试的行为为准描述，候选实现复现同样的行为即判通过，任务语义与参考实现保持一致。依赖网络、文件系统或系统时间的函数无法稳定对照，需在抽取阶段剔除，这部分约占候选函数的一成。额外成本是每条测试多执行一次参考实现，判分容器时间约增加 15%。

### 1.2 语句依赖图与调用图的依赖切片

> **🗣️ 话术——语句依赖图与调用图的依赖切片**：整仓供给时，一条测试合成请求里混着数百个无关定义，同名但语义不同的辅助函数会被模型误用，上下文均值约 2.4 万 token。方案为从目标函数出发做依赖切片：先在语句级依赖图上收集函数体引用的定义，再用 PyCG 调用图补全跨文件调用，只把执行闭包交给合成模型。切片深度扫描了 1、2、3、5 层与全展开：1 层只有 71% 的函数无缺失符号，3 层达到 96.5%，5 层与 3 层相当但上下文长约四成。定稿取 3 层，上下文均值降至约 9.6 千 token，测试一次执行通过率保持 72% 不变。动态导入与反射等静态分析无法解析的引用，按保守策略整体纳入对应模块。

**动机**：测试合成需要让模型理解目标函数依赖的类型、常量与辅助函数。整仓或整文件供给有两个问题。第一是干扰：一个中等规模仓库有数百个函数，与目标函数无关的同名辅助函数（如多个模块各有一个 `normalize`）会被模型错误引用，生成的测试调用了不存在于目标依赖链上的接口。第二是成本：整仓上下文均值约 2.4 万 token，大仓库超过合成请求 32K 的上限后被截断，截断位置随机，关键定义可能恰好被截掉。按物理位置截断（只给目标所在文件）又会漏掉跨文件依赖。这一环需要的是按执行关系选择上下文，选择依据是目标函数运行时实际会用到哪些定义。

**做法**：
1. 语句级依赖图。把每个源文件解析为 AST，以语句为节点，标出定义语句（函数、类、全局赋值）与导入语句；目标函数体中出现的每个名字，沿作用域规则连边到它的定义语句。默认参数、装饰器、类型注解中引用的名字同样连边。
2. 跨文件调用图。用 PyCG 生成调用图，目标函数体中出现 `pkg.utils.helper()` 时，由调用图给出 `helper` 的定义位置并纳入闭包，再从 `helper` 继续向下展开。
3. 深度控制。从目标函数起按调用深度计层，默认展开 3 层；外部第三方包不展开，只保留 `import` 语句，判分镜像中这些包已安装。
4. 动态引用。`importlib.import_module`、`getattr(obj, name)` 这类静态无法解析的引用，按保守策略把出现动态导入的模块整体纳入；仍无法解析的名字进入保留白名单，执行前检查符号完整性。
5. 数值演算。以一个 1.2 万行的仓库为例，整仓上下文约 2.4 万 token（已去除注释与测试目录）；3 层切片平均保留约 40 个定义，约 9.6 千 token，9,600 / 24,000 = 40%，即缩短约六成。按单批 1 万条合成请求计算，输入 token 由 10,000 × 24,000 = 2.4 亿降到 10,000 × 9,600 = 0.96 亿，合成推理耗时随之下降约 45%（输出长度不变，节省部分来自 prefill）。

**取值依据**：关键参数是切片深度。扫描结果为：1 层无缺失符号的函数占 71%，缺失的多为二级辅助函数，模型只能猜其行为；2 层为 89%；3 层为 96.5%；5 层为 97.1%，上下文比 3 层长约四成；全展开没有额外收益，且少数高耦合函数的闭包超过 32K。3 层是符号完整率的拐点，再加深只增加上下文长度。

**收益**：合成上下文均值由约 2.4 万 token 降至约 9.6 千 token；3 层切片下 96.5% 的函数无缺失符号；在等价性断言已开启的条件下，测试一次执行通过率保持 72%，说明缩短上下文没有降低合成质量。切片后超出 32K 被截断的请求由约 6% 降到 0.3%。

**适用边界与代价**：切片依赖静态分析的准确性，大量使用元编程、运行时注册（插件机制、ORM 动态字段）的仓库，切片会遗漏符号；保守策略能保证可执行，代价是这类仓库的上下文明显变长。PyCG 对大仓库的调用图构建较慢，单仓库可达数分钟，抽取阶段需要 64 进程并行；调用图结果按仓库缓存，同一仓库的多个函数共享一次构建。

### 1.3 运行时插桩的真实调用样本采集

> **🗣️ 话术——运行时插桩的真实调用样本采集**：模型凭直觉构造的测试输入过于典型，例如 `"hello"`、`[1, 2, 3]`，覆盖不到真实调用中带首尾空格、混合分隔符或超长列表的边界情形。方案为在目标函数上挂 hook，运行仓库自带测试与示例时记录真实调用的入参、返回值、类型与调用者，入参用签名绑定并展开默认值。超长值保留首尾各 90 字符并插入省略标记，每个函数保留最近 3 条记录，随合成请求作为数据示例提供。有副作用的函数（写文件、发网络请求）不启用采集。开启采集后，边界输入覆盖相对提升约 20%，测试一次执行通过率由 72% 提升至 74%。

**动机**：合成测试的第一步是构造输入。模型在只看到签名与规格时，倾向于给出最典型的输入，测试能执行通过，但覆盖不到函数在真实调用链中真正处理的数据形态：带对齐空格的文本、含 `None` 的列表、嵌套字典、按特定顺序排好的序列。这些形态正是边界分支所在的位置，覆盖不到就会出现覆盖率低于门槛、需要多轮反馈修补的情况。另一类问题是隐式前置条件：有的函数要求输入已排序或非空，模型构造的随机输入违反前置条件，测试在参考实现上直接报错，被自等价校验拦截，浪费一次合成。真实调用样本同时解决这两类问题：它展示了输入的真实形态，也天然满足前置条件。

**做法**：
1. 采集入口。在抽取阶段对仓库执行自带测试套件与 `examples/` 下的示例脚本，通过 hook 包装目标函数。
2. `before_call`：用 `inspect.signature(func).bind(*args, **kwargs)` 绑定实参，调用 `apply_defaults()` 展开默认参数，记录每个参数的值与类型；展开默认值使合成模型能看到调用方依赖默认值的分支。
3. `after_call`：记录返回值与类型；抛出异常时记录异常类型与消息。同时记录调用者的模块与函数名。
4. 序列化。`datetime`、`Decimal`、`Path` 等类型按专门规则转为可读文本；超过 180 字符的值保留前 90 与后 90 字符并插入省略标记，保证片段语法完整，模型能判断这是一条长数据。
5. 写入合成请求。每个函数保留最近 3 条记录，按调用者去重后附在规格之后，标注为「真实调用示例」。无记录的函数走仅规格合成路径，单独统计。
6. 数值演算。4.6 万个候选函数中，约 61% 在自带测试或示例中被调用过、获得至少 1 条记录；按每条记录序列化后平均约 120 token、每函数 3 条计算，单个合成请求增加 120 × 3 = 360 token，相对切片后的上下文为 360 / 9,600 ≈ 3.8%。

**取值依据**：关键参数是每函数保留的记录数。扫描了 1、3、6 条：1 条时边界输入覆盖相对提升约 9%，模型容易把唯一样本当作全部输入形态；3 条时约 20%；6 条时约 21%，但合成请求增加约 720 token，且同一调用者的重复样本增多。截断阈值取首尾各 90 字符：阈值过短时 JSON、SQL 一类结构化字符串被截成无法辨认的片段，过长时单条记录可达数千 token。

**收益**：在等价性断言与依赖切片已开启的条件下，开启插桩采集后边界输入覆盖相对提升约 20%，测试一次执行通过率由 72% 提升至 74%（+2pp）。收益主要体现在测试深度（覆盖边界分支），对能否执行通过的影响较小，这与它在首轮覆盖率达标率上的作用一致。

**适用边界与代价**：采集依赖仓库自带测试或示例，约 39% 的函数没有真实调用记录，只能走仅规格合成路径。有副作用的函数若启用采集，合成出的测试会真实写文件或发请求，污染判分环境，因此按函数名与调用链特征过滤这类函数。执行仓库测试套件本身有成本，每个仓库平均约 4 分钟，安装失败的仓库直接跳过采集。

### 1.4 执行报错与未覆盖分支的多轮反馈

> **🗣️ 话术——执行报错与未覆盖分支的多轮反馈**：一次生成难以同时满足测试可执行与覆盖率达标，首轮覆盖率达标率只有 45%。方案为逐轮只处理未达标函数，按失败原因分两类反馈：执行报错时回传异常类型、消息与出错行，覆盖不足时回传未覆盖分支的位置、条件表达式与已覆盖分支数。终止条件为单函数分支覆盖率不低于 0.8 且整批达标函数占比不低于 0.8，或达到 3 轮上限。达标比例门槛扫描过 0.7、0.8、0.9 三档，0.9 档第四、五轮新增达标不到 3%，容器成本翻倍。覆盖率达标率由首轮 45% 提升至第二轮 71%、第三轮 87%，第二、三轮的容器用量分别约为首轮的 55% 与 29%。

**动机**：测试合成有两个目标：测试能在参考实现上执行通过，测试覆盖函数的主要分支。一次生成时两个目标常常冲突：模型为了覆盖更多分支构造复杂输入，导致执行报错；为了保证执行通过只写简单用例，覆盖率又不够。首轮只有 45% 的函数达到分支覆盖率 0.8。直接丢弃未达标函数会使候选减少过半，而对全部函数重新生成又会把已达标函数反复送进容器，浪费判分资源。反馈需要指向具体问题：只告诉模型「失败了」，模型会重写整份测试，常常把已经正确的用例改错。

**做法**：
1. 每轮四步：对工作清单中的函数生成或修复测试；打包送入沙箱批量执行，回收逐测试结果与分支覆盖率；按结果分流；用未达标子集更新工作清单。
2. 分流规则：执行通过且覆盖率不低于 0.8 的函数达标出列；执行通过但覆盖率不足的标记为补充覆盖，附未覆盖分支提示；执行未通过的标记为修复报错，附异常信息。
3. 修复报错的反馈内容：异常类型、异常消息、出错的测试函数与行号，要求只修改出错的测试函数。
4. 补充覆盖的反馈内容：未覆盖分支所在行、对应的条件表达式（如 `if not sep:`）、当前已覆盖分支数与总数，要求新增用例而不删除已有用例。
5. 数值演算。首轮处理 3.8 万个通过自等价校验的函数，达标 45%；第二轮处理约 2.09 万个未达标函数，累计达标率升至 71%；第三轮处理约 1.1 万个，累计达标率 87%。三轮容器用量合计为 3.8 + 2.09 + 1.1 ≈ 7 万函数次，若每轮都对全部函数重跑则为 11.4 万函数次，增量重试节省约 39%。

**取值依据**：关键参数是单函数覆盖率门槛与整批达标比例门槛。单函数覆盖率门槛取 0.8：取 0.95 时大量函数受限于防御性分支（如参数类型检查后的 `raise TypeError`）无法覆盖，达标率停在 60% 左右；取 0.5 时测试只覆盖主路径，作为判分区分度不足。整批达标比例扫描了 0.7、0.8、0.9：0.7 档两轮即终止，入库任务减少约 12%；0.9 档需要五轮，第四、五轮新增达标不到 3%，容器成本翻倍；取 0.8，三轮终止。

**收益**：覆盖率达标率由首轮 45% 提升至第二轮 71%（+26pp）、第三轮 87%（+16pp）。增量重试使第二、三轮的容器用量分别约为首轮的 55% 与 29%，三轮总用量比全量重跑节省约 39%。分类反馈使修复轮中已正确用例被改错的比例低于 2%。

**适用边界与代价**：剩余约 13% 未达标的函数多依赖外部状态（数据库连接、环境变量）或输入难以构造（复杂对象图），继续重试收益很低，按长尾直接淘汰。分支覆盖率只衡量测试执行了哪些分支，不衡量断言是否充分；断言强度由等价性对照保证，两者需要同时满足。每轮需要一次完整的沙箱执行，轮数上限决定了单批的总耗时，3 轮约 9 小时。

### 1.5 docstring 与已通过测试的规格提炼

> **🗣️ 话术——docstring 与已通过测试的规格提炼**：直接使用 docstring 作为任务规格时，约三成 docstring 只有一句「Returns a list of fields.」一类描述，模型无法据此写出与参考实现行为一致的实现。方案为以 docstring、签名与已通过的等价测试为材料重写规格，测试验证过的边界与异常行为直接成为规格中的输入输出示例与异常约定，规格长度控制在 3 至 8 句。任务包对模型只暴露签名与规格，判分测试隐藏。训练集与评测集按仓库维度切分，并过滤与公开基准重叠的仓库。规格由合成 teacher 重写后，再用一个独立的 Qwen3-32B 实例只读规格实现函数，用隐藏测试判分，通过率低于 10% 的任务回到重写环节，约占 8%。

**动机**：任务包的可解性取决于规格。docstring 由仓库作者写给使用者看，常常省略边界行为：空输入返回什么、分隔符为空时抛什么异常、浮点数如何舍入。规格缺失这些信息时，模型写出的实现在边界上与参考实现不同，被隐藏测试判为失败，失败原因在规格不足，与模型能力无关，评测分数与训练 reward 都会因此失真。另一个问题是污染：如果训练集与评测集包含同一仓库的不同函数，模型可能凭记住的仓库源码得分。

**做法**：
1. 规格材料三份：docstring 提供意图与参数语义；签名提供类型约束；已通过自等价校验与覆盖率门槛的等价测试提供已验证的行为细节。
2. 由合成 teacher（Qwen3-Coder-480B-A35B-Instruct-FP8，temperature 0.3）把三份材料合并改写为 3 至 8 句规格：第一句写功能，其后写参数约定，最后给 1 至 2 个取自测试输入的示例与异常约定（异常类型与消息原文）。
3. 可解性检查：用独立部署的 Qwen3-32B 只读签名与规格实现函数，采样 4 次，用隐藏测试判分；4 次全部失败的任务退回重写，第二次仍全部失败则剔除。
4. 打包与切分：任务包字段为 `task_id / signature / spec / source_ref / test_source / coverage / verdict`；按 `source_ref` 的仓库维度划分训练集与评测集，同一仓库只出现在一侧；与公开代码基准使用的仓库重名者列入黑名单过滤。
5. 数值演算。经过三轮反馈达标的约 1.6 万条任务进入规格提炼；可解性检查首次退回约 8%（约 1,280 条），重写后仍失败约 3%（约 480 条）被剔除；再经去污染过滤约 1,500 条，最终入库约 1.4 万条，相对 4.6 万个候选函数留存约三成。

**取值依据**：关键参数是规格长度与可解性检查的采样次数。规格长度试过不限长度、3 至 8 句、不超过 3 句三种：不限长度时 teacher 会把测试代码逐行翻译成自然语言，相当于泄露判分测试；不超过 3 句时示例与异常约定放不下，可解性检查退回率升到约 19%。可解性检查采样 4 次：采样 1 次时，偶然失败会把可解任务误退回，误退比例约 6%；采样 8 次的结论与 4 次基本一致，推理成本翻倍。

**收益**：规格提炼后，可解性检查的首次退回率约 8%；对照直接使用 docstring 作为规格，同一检查的退回率约 31%。按仓库切分与黑名单过滤保证评测集中的仓库不出现在训练集中。入库任务同时服务评测（只给签名与规格，执行隐藏测试打分）与短程训练（作为可验证样本进入 SFT 池，或以隐藏测试通过率作为 RL 的 reward）。

**适用边界与代价**：规格以参考实现的行为为准，参考实现的怪异行为（如空输入返回 `[""]`）会被写进规格，任务考察的是复现既定行为，与「写出合理实现」略有差别。可解性检查依赖一个中等能力的模型，过难的任务会被误剔除，入库任务的难度分布因此偏向中低难度；需要难题时，单独保留检查失败但人工确认可解的任务。重写与可解性检查合计约占合成推理成本的 30%。

## 二、项目二：仓库级编码 Agent 长程轨迹的质量筛选与增强蒸馏

> **🎯 项目整体话术**：项目二面向仓库级编码任务：Agent 接收一份整库规格，在空工作区从零实现一个可安装、可导入的 Python 库，判分在新容器中运行上游仓库的原有测试，单条轨迹上百轮工具调用、数万 token。任务库与 rollout 由团队完成，项目二从轨迹导出开始，依次做 stream-json 消息聚合与配对校验、失败断言到出错动作的归因、关键决策点的过程监督注入、压缩恢复样本合成，最后在 Qwen3-32B 上做全参蒸馏 SFT 并扫描增强样本配比。对 2,700 余条轨迹处理后入训 2,310 条样本，与初版数据同超参对照，盲改次数下降 38%，接口签名错位率下降 62%，工具报错率减半，总分差异处于噪声量级。本人负责过程监督注入与压缩恢复样本合成两个模块的设计与实现，参与轨迹导出、失败归因与配比实验。

**🏗️ 业界标准 pipeline**

业界常见的长程轨迹蒸馏依次为并行 rollout 采集、轨迹导出、规则过滤与 LLM judge 打分、SFT 打包、蒸馏训练，训练样本基本按原轨迹原样打包。仓库级任务的 rollout 与判分使用一套开源的「规格、从零重建、运行测试、判分」工具链：任务以 Docker 镜像发布，判分时删除模型写入的测试目录与打包配置，基于官方镜像重建容器并执行 `pip install -e .` 与上游测试。项目二的改动挂在导出之后：导出环节补消息聚合与全局索引，过滤环节补到具体动作的归因，打包前增加两类增强样本，训练环节做配比扫描。

### 2.1 stream-json 轨迹的消息聚合与配对校验

> A 题名：stream-json 轨迹的消息聚合与配对校验

> **🗣️ 话术——stream-json 轨迹的消息聚合与配对校验**：rollout 日志按 stream-json 逐块输出，同一轮的思考、文本与多次工具调用被拆成多条记录，直接逐条转成训练消息会产生重复的 assistant 轮次与找不到对应调用的孤立工具结果。方案为导出时按 message id 合并同一轮的全部内容块，转为 OpenAI messages 格式，为全部消息重建全局索引 `g{N}`。随后校验三项：每个 `tool_calls[].id` 都有且只有一个对应的 `tool_call_id`，assistant 与 tool 消息交替顺序合法，轨迹末尾没有未返回的调用。任一项失败的轨迹整条剔除，约占 3%；合并重复轮次后，单条轨迹的 assistant 消息数平均减少约 37%。全局索引是后续归因定位出错动作、注入定位决策点、压缩定位切点的共同依据。

**动机**：rollout 使用的编码 Agent 运行时以 stream-json 形式输出事件流，一个 assistant 轮次可能包含思考、文本与三四次工具调用，它们在日志里是若干条带同一 message id 的记录，工具结果则是独立记录。若按记录逐条转换，一个轮次会变成多条连续的 assistant 消息，工具结果与调用的对应关系依赖记录顺序，一旦日志中出现乱序或截断，就会生成孤立的工具结果。这类样本进入 SFT 后，模型会学到连续多次发言或凭空出现的工具返回；在 chat template 层面，部分模板对 assistant 与 tool 的交替顺序有硬性要求，格式错误的样本会在 tokenize 阶段报错，或被静默截断。另一个需求来自下游：归因、注入与压缩都需要精确定位「第几轮的哪个动作」，原始日志中的记录序号随内容块数量变化，不能作为稳定的位置标识。

**做法**：
1. 按 message id 聚合：把同一 message id 下的思考块、文本块与 tool_use 块合并为一条 assistant 消息，tool_use 转为 `tool_calls` 列表，保留原始顺序。
2. 工具结果转换：每个 tool_result 转为一条 `role: tool` 消息，`tool_call_id` 取自原记录。
3. 全局索引：聚合后按顺序给每条消息编号 `g0, g1, ...`，写入消息元数据；索引在后续所有处理中保持不变，增强操作只追加内容，不重新编号。
4. 三项校验：调用与返回一一对应；角色交替合法（tool 消息必须紧跟包含对应调用的 assistant 消息）；末尾没有悬空调用。失败即整条剔除，并记录失败类型。
5. 完整存档：导出时另存一份未截断的完整轨迹，后续注入与压缩从完整存档读取，避免从截断版本写回时丢失末尾内容。
6. 数值演算：2,700 余条轨迹中，配对校验失败约 3%（2,700 × 3% ≈ 81 条），其中约六成来自 rollout 超时被强制结束、最后一次调用没有返回，约四成来自日志写入中断；剔除后约 2,620 条进入归因与筛选，筛选保留 1,730 条成功轨迹，1,730 / 2,620 ≈ 66%。

**取值依据**：关键选择是校验失败时整条剔除还是修补。试过两种修补：删除孤立的工具结果，或为悬空调用补一条空返回。删除孤立结果会让模型看到「调用后没有任何返回就继续推理」的形态；补空返回会让模型学到对空结果的错误反应。两种修补在抽检中都产生了不自然的样本，而失败轨迹只占约 3%，剔除带来的数据减少可以接受，因此定稿为整条剔除。

**收益**：校验后的训练集中工具调用配对错位为零，tokenize 阶段没有格式报错；全局索引使归因能把失败断言定位到具体轮次，使注入与压缩切分的位置可复现。与按记录逐条转换的旧导出相比，单条轨迹的 assistant 消息数平均减少约 37%（重复轮次被合并），平均样本长度相应缩短。

**适用边界与代价**：聚合依赖运行时日志中 message id 的完整性，换用其他 Agent 运行时（如 OpenHands 一类）时需要重写解析逻辑。校验只检查结构，不检查内容质量，内容质量由归因与筛选环节处理。完整存档使存储量约翻倍，2,700 余条轨迹的完整存档约 9GB。

### 2.2 失败断言到出错动作的三层归因

> **🗣️ 话术——失败断言到出错动作的三层归因**：低分轨迹只看总分，无法区分环境问题、任务问题与模型行为问题，也就无法决定一条轨迹该丢弃、修复还是保留。方案为三层证据链：判分层从测试输出取失败断言、报错类型与 file:line；轨迹层沿全局索引回溯最后一次改动该文件的 Write 或 Edit，定位引入错误的轮次；归因层把失败归入九类模式并标注严重度。统计时按出现频率与命中样本均分两列分开报告，并且只在全量轨迹上统计。在上游测试通过率不足 0.5 的约 1,100 条轨迹中，超过 95% 归因到自测与判分验证方式不一致；未完成类只有 12 条，命中样本均分 0.07。归因结论用于筛选规则：答案获取类整条剔除，环境失败类重投，其余按通过率与盲改计数分流。

**动机**：仓库级任务的判分是上游测试的整体通过率，一条轨迹得 0.2 分，可能是因为包结构错误导致测试在 collection 阶段全部报错，也可能是实现了大部分功能但接口签名与上游不一致，还可能是容器安装依赖失败。三种情况对训练数据的意义完全不同：第一种说明轨迹中有未经验证就宣告完成的行为，不能入训；第二种说明实现过程有价值，问题集中在少数接口；第三种与模型无关，应重投。只按总分阈值过滤，会把第三种误删、把第一种中分数偶然偏高的样本保留下来。归因要回答的是「哪一步动作导致了哪一条测试失败」，这需要把判分输出与轨迹中的具体动作对齐。

**做法**：
1. 判分层：解析上游测试的完整输出，提取每条失败用例的名称、报错类型与 file:line；collection 阶段的报错单独标记。
2. 轨迹层：对每个出错文件，沿全局索引倒序查找最后一次写入或编辑该文件的 Write 或 Edit，记录其索引；若报错为 `ImportError` 或 `ModuleNotFoundError`，额外查找是否从未创建对应包目录的初始化文件。
3. 归因层：结合前两层的证据归入九类失败模式：过早终止（未执行验证即宣告完成）、未完成、上下文截断、导航空转（反复 ls 与 Read 而无有效编辑）、盲改、依赖与包结构失败、自测与判分验证方式不一致、资源耗尽、答案获取（下载目标包源码或读取判分材料）。每类按高、中两档标注严重度。
4. 统计：两列分开计算，一列是命中该类的轨迹数，一列是命中轨迹的平均得分；只在全量轨迹上统计，不在按低分筛出的子集上统计。
5. 接入筛选：答案获取类整条剔除，判定只看实际执行的工具调用的 command 与 url 字段；环境安装失败类重投；其余轨迹按上游测试通过率与最长盲改分流。
6. 数值演算：约 2,620 条轨迹中，上游测试通过率不足 0.5 的约 1,100 条；归因到验证方式不一致的超过 95%，其中约 46%（1,100 × 46% ≈ 506 条）同时命中依赖与包结构失败（collection 阶段报错），约 38%（约 418 条）同时命中过早终止（自测全部通过但接口与上游不一致）；未完成类只有 12 条，平均得分 0.07。

**取值依据**：关键选择是统计范围。曾在按低分条件筛出的子集上统计答案获取类的影响，得出「答案获取没有带来高分」的结论；在全量上统计结果相反，答案获取类轨迹的平均得分明显高于其余轨迹。原因是低分子集的筛选条件系统性排除了高分轨迹，而答案获取恰好集中在高分区。因此定稿为成因统计一律使用全量，必须使用子集时写明子集条件与被排除的样本。

**收益**：归因使低分轨迹的处理从统一丢弃变为按原因分流：环境失败类重投后回收约 6% 的轨迹；答案获取类在入训前全部剔除；验证方式不一致这一结论直接决定了后续增强的方向，过程监督注入的首要触发点就是完成宣告前的核对。

**适用边界与代价**：轨迹层的回溯规则（最后一次改动该文件的动作）对跨文件的接口错误不够准确，例如错误在核心模块的函数签名，报错却出现在接口模块的调用处，此时需要结合报错栈多看一层。九类模式之间不互斥，一条轨迹通常命中两到三类，统计时按类分别计数，不能把各类占比相加。归因全部基于规则与解析，不调用 LLM，单条轨迹耗时约 2 秒，但新的失败形态需要人工补规则。

### 2.3 关键决策点的过程监督注入

> **🗣️ 话术——关键决策点的过程监督注入**：成功轨迹中仍有假完成、盲改、规划流于形式与压缩后退化四类问题，共同原因是模型知道自己做过什么，却缺少对「还差什么、处在哪个阶段」的判断。方案为在成功轨迹的九类关键决策点前置写入一段英文状态回顾，只写已完成什么、还差什么、验证依据是什么，不给操作指令。完成宣告点必注入，其余候选点按调和平均式预算与最小间隔分配，单条轨迹候选注入点上限 10 个，实际平均 3 至 4 处。注入只修改该条 assistant 消息的 content，不改动 tool_calls 与返回的配对。注入文本由 Qwen3-235B-A22B-Instruct-2507 生成，质量门只用关键词规则，不达标时丢弃该注入点、保留整条轨迹。训练后，宣告完成前未执行任何测试的轨迹占比由 23% 降至 9%。

**动机**：归因显示，低分的首要原因是自测与判分验证方式不一致，表现为模型在未执行上游风格测试的情况下宣告完成。即使在成功轨迹里，同样的行为也存在，只是这次结果恰好正确。按原样蒸馏，学生学到的是「写完就宣告完成」的动作序列，宣告前核对状态的习惯没有出现在数据里。一种常见做法是给每一轮打结构化阶段标签（如「阶段：实现中」），但这种标签与推理时模型的自然输出形态不一致，学生会学会复述标签格式，状态判断能力并不随之提高。需要的是在少数关键位置，用自然语言写出一段与该位置真实状态一致的回顾。

**做法**：
1. 触发点识别。沿全局索引扫描九类主触发点：完成宣告（「任务完成」「全部通过」一类表述）、报错到修复的拐点、首次执行测试、最后一次执行测试的前一轮、任务阶段边界、任务分解完成后的首次编辑、盲改段起点、盲改段终点（连续写改后首次执行验证）、规划清单更新点；另设 token 突增点与重读密集点两类备选触发点，主触发点不足时启用。
2. 采样预算。候选数为 $n$、上限为 $S=10$ 时，基础预算为 $\mathrm{base}=\max(1,\lfloor nS/(n+S)\rfloor)$；轨迹超过 10 万字符加 2，超过 5 万字符加 1，截断到 $[1,S]$ 得到 $e$；候选点之间的最小间隔为 $\max(2,\lfloor n/(e+1)\rfloor)$，避免注入点聚集。完成宣告点不占预算，必定注入。
3. 生成。把触发点之前的完整轨迹与触发点之后真实发生的 3 个动作交给注入模型（Qwen3-235B-A22B-Instruct-2507，temperature 0.6），要求用英文、第一人称、自然叙述写出 2 至 5 句状态回顾；规划类注入需与之后真实发生的动作一致。
4. 写回。注入文本前置拼接到该条 assistant 消息的 content，`tool_calls` 字段不变；写回时从完整存档读取。
5. 质量门。只用规则：长度在 40 至 120 词之间；包含状态类词组（completed、remaining、not yet verified 等）；完成宣告点的注入必须提及验证依据；不达标丢弃该点。
6. 数值演算。以一条 n=24 个候选点、长 7 万字符的轨迹为例：$\mathrm{base}=\lfloor 24\times10/34\rfloor=7$，长度加权后为 8，最小间隔 $\max(2,\lfloor 24/9\rfloor)=2$；质量门通过约 45%，最终写入 3 至 4 处。全部 1,730 条成功轨迹中，444 条在至少一个完成宣告点或测试执行点写入了通过质量门的注入，作为注入版样本，原版同时保留。

**取值依据**：关键参数是候选注入点上限 S 与注入版样本的保留方式。S 扫描了 5、10、20：S=5 时长轨迹的中后段几乎没有注入点；S=20 时单条轨迹平均注入 7 处以上，注入文本在样本中占比过高，学生在推理时出现在每次工具调用前都写一段回顾的倾向；取 10。注入版与原版并存：只保留注入版时，学生的回顾频率偏高；并存时，学生在关键位置写回顾，在常规编辑位置直接调用工具。

**收益**：与只加导出校验与归因筛选的配置相比，加入注入版样本后，每条评测轨迹的盲改次数由 4.4 降至 3.9；宣告完成前未执行任何测试的轨迹占比由 23% 降至 9%。抽查学生轨迹，完成宣告前出现「列出已实现模块、说明哪些尚未验证、随后执行测试」的形态，这一形态在初版数据训练的学生中很少出现。

**适用边界与代价**：注入只能写在成功轨迹上，失败轨迹的后续动作本身是错的，回顾与后续动作对齐会强化错误路径。注入依赖一个能读完整条数万 token 轨迹的大模型，8×H100 约 5 小时处理 1,000 条轨迹。注入文本风格若与学生自身的思考风格差异过大，会出现两种风格交替的输出，因此注入版样本占比需要通过配比实验控制。

### 2.4 九段摘要模板的压缩恢复样本合成

> **🗣️ 话术——九段摘要模板的压缩恢复样本合成**：推理时上下文达到上限会触发压缩，压缩后的模型常凭记忆直接编辑文件，或反复重读同一批文件，对照组中经历过压缩的轨迹中位得分约为未压缩轨迹的一半。训练数据默认都是完整上下文，学生没有见过只剩摘要的形态。方案为把长轨迹切成两段：前段原样保留，后段的历史改由九段有损摘要重建，摘要覆盖主要诉求、关键技术概念、文件与代码段、错误与修复、问题解决过程、用户消息、待办任务、当前工作与下一步。切点在累积约 5 万 token 后，取紧邻下一次重读或测试的轮边界，尾部至少保留 4 轮。恢复引导要求先确认再修改，且不得出现 compaction、summary 等自指词。一批 136 段样本工具调用配对零错位，学生最长盲改由约 8 轮降至约 4 轮。

**动机**：仓库级任务的轨迹常超过 10 万 token，推理时运行时会在接近上限时把早期历史压缩为摘要。压缩后的上下文缺失了文件的具体内容与已执行过的验证结果，模型常见两种退化：凭记忆中的文件内容直接 Edit，`old_string` 匹配失败或覆盖了已修改过的代码；或者失去对任务状态的把握，反复 Read 同一批文件而没有进展。对照组中，经历过压缩的轨迹中位得分约为未压缩轨迹的一半。问题的根源在训练数据：蒸馏样本全部是完整上下文，学生从未见过「前面只剩一段摘要」的输入，压缩后的第一个动作没有任何示范。

**做法**：
1. token 估算：逐轮累加消息长度，按字符数除以 3 粗估 token，全链路统一使用这一口径。
2. 切点选择：累积达到约 5 万 token 后不立即切分，向后查找第一个满足两项条件的轮边界：下一轮的工具调用包含 Read，或 Bash 命令包含 pytest、unittest 或测试脚本；切点之后至少还有 4 轮。切点只落在轮边界上，保证每段的调用与返回成对。
3. 摘要生成：用与推理时运行时一致的九段模板，对切点之前的历史生成有损摘要，每段 1 至 5 句；附两条系统提醒，内容为最后一次 Read 的文件路径与截断后的内容。
4. 后段组装：任务规格、摘要消息对、续接前缀、恢复引导与切点之后的原始消息依次拼接。恢复引导要求「直接继续，先确认文件当前内容与测试状态再修改」。
5. 质量门：恢复引导与摘要中不得出现 compaction、summary、context limit 等词，因为推理时的指令要求模型不提及摘要；恢复引导须包含 confirm、re-read、run the test 等验证类词组；逐段复核调用配对。
6. 数值演算：1,730 条成功轨迹中，超过 9 万 token、可以切分且满足尾部条件的有 136 条，每条切出 A、B 两段；A 段与原轨迹前缀重合，不单独计入，B 段 136 条作为压缩恢复样本，平均长约 4.1 万 token（摘要约 3 千 token 加尾部原始消息约 3.8 万 token，3,000 + 38,000 = 41,000）；136 / 2,310 ≈ 5.9%。

**取值依据**：关键参数是切分阈值。扫描了 3 万、5 万、8 万 token：3 万档每条可切出 3 段以上，摘要在样本中的占比过高，学生倾向于在没有压缩的场景也先输出一段总结；8 万档只有约 28% 的长轨迹满足尾部条件，样本太少；取 5 万，比推理时真实的压缩点更早，可以从中等长度的轨迹中也切出样本。切点顺延到重读或测试轮次，是为了让 B 段的第一个动作就是重读或验证；直接在阈值处切分时，约四成 B 段的第一个动作是 Write 或 Edit，相当于示范「压缩后接着盲改」。

**收益**：一批 136 段样本工具调用配对零错位，质量门删除的样本约 3%。与加入注入版之后的配置相比，再加入压缩恢复样本，每条评测轨迹的盲改次数由 3.9 降至 3.1，学生最长盲改由约 8 轮降至约 4 轮。在评测中触发压缩的任务上，压缩后第一个动作是重读或执行测试的比例由约 41% 升至约 78%。

**适用边界与代价**：九段摘要模板须与推理时运行时的摘要格式一致，换用不同运行时时需要同步改模板，否则训练与推理的输入形态不一致。摘要由模型生成，属于有损压缩，个别样本的摘要遗漏了关键约束，后段的动作在摘要中找不到依据，这类样本只能靠抽检发现。压缩恢复样本只占入训量约 6%，效果集中在长任务上，对短任务没有可测量的影响。

### 2.5 增强样本配比扫描与长序列蒸馏 SFT

> **🗣️ 话术——增强样本配比扫描与长序列蒸馏 SFT**：学生为 Qwen3-32B，原生上下文 32K，仓库级轨迹均长约 3.6 万 token、最长超过 10 万 token，训练时用 YaRN 因子 4 把上下文扩到 128K。SFT 为全参更新，只对 assistant 消息计 loss，lr 1e-5 cosine，warmup 3%，global batch 16 条序列，2 epoch 共 290 步，16×H100 约 12 小时。训练集由 1,730 条成功轨迹与两类增强样本组成，增强样本占比扫描了 15%、25%、35%、45% 四档：占比上升时行为指标持续改善，超过三成后，同类状态下的回复在注入风格与原轨迹风格之间来回切换，取 25%。与初版数据同超参对照，盲改次数下降 38%，接口签名错位率下降 62%，工具报错率减半，96 个 held-out 任务上的均分差异处于噪声量级。评测时得分变化按训练前是否依赖答案获取分组拆分，行为指标与得分分开报告。

**动机**：增强样本与原始轨迹在文本风格上存在差异：注入版在关键位置多了一段第三方模型写的回顾，压缩恢复段的开头是一段摘要。增强样本占比过低时，学生学不到新行为；占比过高时，学生会把增强样本的形态当成默认形态，在不需要回顾的位置也写回顾。另一方面，Qwen3-32B 原生上下文 32K，而入训样本均长约 3.6 万 token，不扩展上下文就必须截断，截断会截去轨迹末尾的验证与完成宣告，这正是项目二最关心的部分。

**做法**：
1. 上下文扩展：在 RoPE 上启用 YaRN，因子 4，原始最大位置 32,768，训练与推理都使用同一配置，序列上限 128K。
2. loss 范围：只对 assistant 消息计 loss，system、user 与 tool 消息全部掩码；注入文本属于 assistant 消息，计入 loss。
3. 训练配置：全参更新，bf16，lr 1e-5，cosine 衰减，warmup 3%，global batch 16 条序列，2 epoch；每 50 步保存一次 checkpoint，选点看 val loss 与行为指标两项。
4. 配比扫描：成功轨迹 1,730 条固定，增强样本按注入版与压缩段约 3:1 的比例增减，分别取占比 15%、25%、35%、45%，其余超参不变，每档在 96 个 held-out 任务上评测 3 次取均值。
5. 评测拆分：评测任务按训练前的学生是否依赖答案获取得分分为两组，分别报告得分变化；行为指标（盲改次数、接口签名错位率、工具报错率、最长盲改）单独成表。
6. 数值演算：入训 2,310 条样本，增强样本 444 + 136 = 580 条，占 25.1%；样本均长约 3.6 万 token，每 epoch 约 2,310 × 3.6 万 ≈ 8,300 万 token；global batch 16 条，每 epoch 约 145 步，2 epoch 共 290 步，平均每步约 57 万 token。

**取值依据**：关键参数是增强样本占比与 epoch 数。占比四档的现象：15% 档盲改次数为 3.6，改善有限；25% 档为 3.1；35% 档为 2.9，但约 11% 的评测轨迹在相邻两轮之间交替出现注入风格的回顾与无回顾的直接调用；45% 档交替比例升至约 24%，接口签名错位率反而回升。取 25%。epoch 取 2：1 epoch 时行为指标只改善约一半；3 epoch 时 val loss 在第二个 epoch 后段开始回升，学生复述训练轨迹中具体文件名的情况增多。

**收益**：与初版数据（成功轨迹原样打包）同超参对照，每条评测轨迹的盲改次数由 5.0 降至 3.1（下降 38%），接口签名错位率下降 62%，工具报错率减半，最长盲改由约 8 轮降至约 4 轮；96 个 held-out 任务的均分差异在 3 次评测的波动范围内。数据量对照中，把增强样本换成同等数量的成功轨迹重复采样，盲改次数只到 4.3，下降主要来自增强样本的内容。得分拆分显示，一轮表观增益中约六成来自残留的答案获取样本，此后答案获取扫描从离线检查前移到打包环节，入库前逐条过滤。

**适用边界与代价**：配比结论与学生的规模和风格相关，换用更大的学生或风格差异更大的注入模型时需要重新扫描。YaRN 扩展后，32K 以内的短上下文任务需要检查是否退化，本项目在通用代码评测上的变化在 0.5pp 以内。128K 序列的训练显存压力大，需要开启 context parallel 与 gradient checkpointing，16×H100 上单步约 2.5 分钟；四档配比扫描与最终训练共 5 次训练，约 60 小时；项目历时约 4 个月。
