## 〇、项目话术速查

> **项目串联逻辑（面试自我介绍时用）**：这两个项目是代码 Agent 后训练数据链路的前后两段。项目一解决「任务供给」——把真实开源仓库代码转化为自带判分能力的函数级编程任务，判分不做期望值预测、改为对照参考实现的行为，上下文用依赖切片控制成本。项目二解决「轨迹质量」——长程编码任务（单条轨迹上百轮工具调用）采集到的数据先过静态预筛与失败模式归因，再把成功轨迹加工成更高质量的训练样本：在关键决策点补写进度回顾、按上下文压缩边界切出压缩恢复样本，最后做蒸馏对照并按来源拆分归因。两个项目合起来覆盖「造题 → 判分 → 采集 → 治理 → 增强 → 蒸馏」的完整数据闭环。

> **P1 一句话**：从 210 余个真实开源仓库构造 1.4 万条带自动判分的函数级编程任务：判分以参考实现（oracle）为基准、消除期望值预测带来的噪声；依赖切片把合成上下文成本降低约六成。
> **P2 一句话**：对 2,700 余条长程编码 Agent 轨迹做质量审计与增强训练——盲写指标预筛、九类失败模式归因、关键决策点过程监督注入、压缩恢复样本合成，增强数据训练后盲改降 38%、接口签名错位降 62%。

## 一、项目一：从真实代码仓库合成函数级编程任务与等价性判分

> **🎯 项目整体话术**：这个项目做的是编程 Agent 的训练与评测任务供给。做法是从 GitHub 真实仓库批量抽取函数，为每个函数合成一份可自动判分的测试，最终产出「签名 + 自然语言规格」形式的编程任务——模型写实现、测试自动判分。数据规模是从 210 余个中高热度 Python 仓库抽取约 4.6 万个函数，筛选后产出 1.4 万条经沙箱验证可判分的任务。核心设计有两个：一是判分不依赖模型预测期望输出，只断言候选实现与参考实现行为一致，原函数就是标准答案，从源头消除判分噪声；二是上下文不提供整个仓库，用依赖切片只保留目标函数真正依赖的定义，平均缩短约六成。结束条件是「分支覆盖率 ≥0.8 且达标函数占比 ≥0.8」，三轮迭代把覆盖率达标率从首轮 45% 提升至 87%。这个项目里我负责等价性判分与依赖切片两个模块的设计与实现，也参与插桩采集和迭代流程的实现。

**🏗️ 业界标准 pipeline**：

> 业界标准的编程任务合成走 `仓库采集 → 函数抽取 → 上下文构建 → 测试合成 → 沙箱执行判分 → 覆盖率筛选入池` 范式——测试合成环节的常见做法是让模型直接生成「输入 → 期望输出」对，上下文环节常见做法是把整个仓库或整文件提供给模型。本项目在判分协议与上下文构造两个环节做了改动：判分不做期望值预测、改为「与参考实现行为一致」的断言；上下文不做整仓供给、改为依赖切片闭包；其余环节沿用业界标准范式。

### 1.1 以参考实现为基准的等价性判分

> **🗣️ 话术——等价性判分**：等价性判分是我负责设计的核心模块。传统做法让模型直接预测测试的期望输出，非平凡函数的输出很容易被预测错；错的期望值一旦入库，判分结果即不可信，判分偏差还会被下游当成模型能力问题。我把判分方式整体替换：测试只断言一件事——候选实现在相同输入下的输出与参考实现一致。原函数本身就是标准答案（oracle），模型不需要知道「正确答案」，只需要写清楚「怎么对比」。另外加了一道自等价校验：新测试先在参考实现上执行，执行失败即判定为测试自身缺陷、入库前拦截，实测拦截约 7%。

**机制拆解**：

1. **为什么「预测期望输出」不可靠**。很多真实函数的输出对 LLM 而言并不直观：`split_fields("a,,b", ",")` 的空字段保留语义、`Decimal` 舍入规则、生成器函数的惰性行为——模型凭直觉写出的期望值经常在边界情形上出错。这类错误两个方向都有危害：真实现被误判为错（假阴）、错误实现被误判为对（假阳），并随数据流入下游训练。
2. **等价性断言的形态**。测试代码不包含字面期望值，而是把候选实现与参考实现放进同一执行环境，对同组输入逐一比对：

   ```python
   def test_normalization_is_equivalent(candidate, reference):
       cases = ["", "  a  ", "A\u00a0b", "line\nbreak"]
       for c in cases:
           assert candidate.normalize(c) == reference.normalize(c)
   ```

   异常路径同样比对：断言两边抛出的异常类型一致、消息一致（或按规格允许的子串）。返回值若含浮点，按等值浮点比较；若含不可直接比较的对象，比较序列化结果。
3. **自等价校验（self-equivalence check）**。每条新生成的测试先在参考实现上执行一遍：
   - 通过 → 测试被认为「自身的期望与参考行为一致」，可进入判分集；
   - 不通过 → 测试自身有缺陷（打错 API 名、环境缺依赖、断言写反、语法错误），判定 `test_defect` 拦截，不进入题库。
   实测拦截约 7% 的缺陷测试；这一步把「测试自身的 bug」与「候选实现的 bug」彻底区分开。
4. **判分在新建的隔离容器中执行**。判分不在写代码的工作区里执行：新建容器，覆盖前先清除打包配置与工作区里的测试目录（防止候选自写的「送分测试」覆盖判分测试），统一用固定的 `PYTHONPATH` 执行。判分只收集行为结果（逐测试 pass/fail），不读取候选实现源码。
5. **初始化噪声的例外清单**。容器初始化阶段偶发的 `SyntaxWarning: invalid escape sequence`、`NameError` 类噪声不计入失败——这类问题多数来自环境而非测试逻辑，直接判失败会引入系统性噪声。

**关键取舍**：为什么不让人工写判分测试？规模不允许（目标量级是万条）。为什么不用静态检查（lint/类型）？静态查不出行为错误，只能查语法与风格。等价性协议的前提是「参考实现可信」，因此素材端做了严格筛选（1.2 的切片与 1.3 的真实 I/O 采集，都是为了给合成模型提供更准确的信息）。

### 1.2 依赖切片缩减合成上下文

> **🗣️ 话术——依赖切片**：依赖切片这个模块是我设计的。最初上下文是整个仓库直接提供给模型，token 成本高是一方面；更麻烦的是一条测试合成任务里混着几百个无关函数，模型容易受到干扰——比如引用到同名但语义不同的工具函数。我改成从目标函数出发做切片：先建语句级依赖图，再用调用图补全跨文件调用关系，只把真正会被执行到的依赖闭包交给模型，深度可配置。效果是上下文平均缩短约六成；测试合成的一次执行通过率提升约 14pp——后一个数字比缩短上下文更有说服力：它说明无关代码的干扰确实减少了。

**机制拆解**：

1. **两类上下文供给的对照**：

   | 供给方式 | 内容 | 问题 |
   | --- | --- | --- |
   | 整仓上下文 | 整个仓库源码（或整文件） | token 高；无关代码干扰；跨引用噪声 |
   | 依赖切片 | 目标函数的执行闭包 | 依赖静态分析的准确性；动态引用需保守处理 |

2. **切片的构造流程**（基于真实实现的 `CodeDependencySlicer`）：

   - **第一步：语句级依赖图**。把源码解析为 AST 后按语句建节点，标出「定义语句」（函数、类定义）与「导入语句」，语句之间的引用关系连边——目标函数体内引用的每个名字，沿边找到它真正指向的那条语句。
   - **第二步：跨文件调用图**。用调用图（PyCG）解析跨文件调用：目标函数调用 `a.b.helper()`，调用图给出 `helper` 的定义位置，切片把它纳入闭包。
   - **第三步：深度控制 + 导入保留**。切片深度默认 3 层（`depth` 可配，-1 为全展开）；`import` 语句按需保留，外部依赖（pip 包）不展开、保留语句本身——判分环境里这些包是装好的。

3. **动态引用怎么处理**。`importlib` 动态导入、`getattr(obj, name)` 反射这类静态分析追不到的引用：保守策略是把动态导入出现的模块整体纳入切片；无法解析的名字进入保留白名单，保证执行时不缺符号（代价是上下文略大）。

4. **效果对比**：

   | 指标 | 整仓上下文 | 依赖切片 |
   | --- | --- | --- |
   | 平均上下文长度 | 基准 | 约 −60% |
   | 测试一次执行通过率 | 基准 | 约 +14pp |

   （工程实测：切片深度 3、动态引用保守处理开启；同一批函数在两种上下文供给下各执行一遍。）

**关键取舍**：为什么不「按文件截断」？文件级截断对「跨文件依赖多」的函数会缺符号，对「单文件大」的函数仍然太长；切片按「执行时会用到什么」来选择，不按代码的物理位置截断。

### 1.3 运行时插桩采集真实输入输出

> **🗣️ 话术——真实输入输出采集**：插桩这块我在项目里负责实现与效果验证：给目标函数挂上 hook，记录真实调用时的入参、返回值、类型与调用者，序列化后写进测试合成的提示里。价值在于测试数据：从模型凭直觉构造，变为真实执行过的样本——模型看到真实输入的形态与返回值的类型，写出的用例边界覆盖和稳定性都更好，边界输入覆盖相对提升约两成。

**机制拆解**：

1. **为什么要真实 I/O**。合成测试的第一步是「造输入数据」：模型凭直觉构造的输入往往过于典型（`"hello"`、`[1, 2, 3]`），而真实调用链里的输入常带业务特征（带空格的对齐文本、混合分隔符、超长列表）。真实捕获的入参直接告诉模型「这个函数实际被怎么调」。
2. **捕获实现**（基于真实实现的 `ArgumentCaptor`）：

   - `before_call`：用 `inspect.signature(func).bind(*args, **kwargs)` 绑定实参，再 `apply_defaults()` 把默认值展开——**默认参数也展开**这一点很关键，否则测试容易漏掉「调用方依赖默认值」的分支；
   - `after_call`：记录返回值与其类型；
   - **序列化**：`datetime`/`Decimal` 等类型用专门规则转可读文本；超长的可迭代对象**截断保留首尾**——保留前 90 与后 90 个字符并插入省略标记，让模型知道「这是一条很长的数据」，而不是得到一个语法不完整、容易被误判为错误的样本；
   - **调用者信息**：同时记录调用者模块与函数名，帮助在合成测试里复现「谁在什么场景下调它」。
3. **写入方式**：每条测试合成请求附带 2–3 条最近的捕获记录（展示输入样例与输出形态），作为数据示例与规格一起给模型；对副作用明显的函数（写文件、发网络请求）先过滤捕获记录，避免把不可复现的调用提供给合成环节。
4. **边界情况**：函数从未被调用（无捕获记录）→ 改走「仅规格合成」路径，这部分任务的占比单独统计，不计入主统计。

**关键取舍**：为什么不直接用「自动生成随机输入」？随机输入覆盖不到真实数据形态（比如真实的业务字符串），且对「输入必须满足隐式约束」的函数（如排序过的列表）会大量生成无效样本。

### 1.4 生成-执行-反馈多轮迭代

> **🗣️ 话术——多轮迭代**：一次生成很难同时满足「测试能够执行通过」和「覆盖率达标」，所以设计了一个多轮迭代流程。每轮筛选出未达标的函数重新生成或修复测试，反馈分两种信号：测试执行报错，返回异常栈和出错行；执行通过但覆盖率不足，把未覆盖的分支整理成提示、让模型补充用例。结束条件是「分支覆盖率 ≥0.8 且达标函数比例 ≥0.8」。实测覆盖率达标率从首轮的 45% 提升到三轮后的 87%——后两轮基本都在处理长尾的难测函数。

**机制拆解**：

1. **闭环四步**（真实实现 `GenerateExecuteAgent` 的循环）：

   ```
   每轮：
     generate   对 worklist 里未达标函数生成/修复测试
     execute    打包测试 → 沙箱批量执行 → 回收逐测试结果与覆盖率
     filter     按结果分流：
                 通过且覆盖率 ≥0.8        → 达标，移出循环
                 通过但覆盖率 <0.8        → 标记 improve_coverage，附未覆盖分支提示
                 未通过                   → 标记 fix_error，附异常栈
     update     用反馈更新 worklist，进入下一轮
   ```

2. **两类反馈信号的渲染差异**：

   - `fix_error`：回传执行异常的类型、消息、出错行——模型据此修测试（打错 API、构造数据不合法等）；
   - `improve_coverage`：把未覆盖的分支整理成结构化提示（分支位置、条件表达式、当前已覆盖数/总数）——模型据此补充边界用例，而不是盲目增加断言。

3. **门槛与终止条件**：分支覆盖率 ≥0.8（单函数）、达标函数占比 ≥0.8（整批）、最多 3 轮；每轮仅处理未达标子集（增量重试），避免把已达标函数反复送进容器——这一条把后两轮的容器成本压到首轮的一成上下。
4. **为什么设「达标比例」门槛而不是要求全部达标**：要求 100% 函数达标，会让长尾（依赖外部状态、难构造输入的函数）无限消耗重试预算；达标比例门槛把资源控制在「能获得足够多合格任务」的水平上，长尾随轮次自然淘汰。

### 1.5 规格提炼与任务集打包

> **🗣️ 话术——规格提炼与打包**：打包这块我负责把「函数 + 已通过测试」整理成任务规格，产出「签名 + 规格」的任务包。规格不直接复制 docstring——部分 docstring 描述粗糙（「Returns a list of fields.」这类），我让模型结合已通过验证的等价测试一起重写：测试里验证过的行为，正是这个函数已经确认过的语义；两者合并提炼后，规格具体到输入输出示例与异常契约这一层。下游评测时只给签名和规格，模型写实现、判分执行隐藏测试；训练时直接进 SFT 池。

**机制拆解**：

1. **规格的三处来源合并**：

   | 来源 | 贡献的信息 |
   | --- | --- |
   | 函数 docstring | 函数意图、参数语义 |
   | 已通过的等价测试 | 已验证的行为细节（边界、异常、返回形态） |
   | 签名 | 类型契约（参数类型、返回类型） |

   提炼过程以「函数 + 已通过测试」为材料做一次改写，产出 3–8 句的规格文本——比 docstring 更具体（含示例），比测试可读（自然语言）。

2. **任务包形态**：`task_id / signature / spec / source_ref / test_source（隐藏）/ coverage / verdict`——下游消费两种形态：
   - **评测**：给 `signature + spec`，模型写实现，判分执行隐藏的 `test_source`；
   - **训练**：作为可验证任务进 SFT/RL 池，判分奖励即测试通过率。
3. **去污染元数据**：`source_ref` 记录仓库 + 文件 + commit——评测集与训练集按仓库维度切分（同一仓库不同函数不与评测集重叠），避免模型因记住仓库源码而虚高。
4. **产出规模**：约 4.6 万候选函数 → 经自等价校验、双门槛迭代、去污染过滤后产出 1.4 万条——留存约三成，损耗集中在两类：难测函数（依赖外部状态、无稳定输入）与被拦截的缺陷测试。

## 二、项目二：长程代码 Agent 轨迹的质量审计与增强训练

> **🎯 项目整体话术**：这个项目做的是长程编码 Agent 的轨迹数据治理与训练。长程任务的单条轨迹是上百轮工具调用、长度数万 token，采集成本高；低质轨迹混进 SFT，会让模型学到两类错误行为：连续编辑不回读验证、宣告完成但从未执行验证。整条链路分五段：静态预筛（用盲写指标先过滤连续写大量文件却不验证的轨迹）→ 失败模式归因（判分输出、轨迹、归因三层证据链，为低分样本定位出错原因）→ 过程监督注入（在成功轨迹的关键决策点补写进度回顾）→ 压缩恢复样本合成（按上下文压缩边界把长轨迹切成多段训练样本）→ 蒸馏对照与来源归因。数据规模是对 2,700 余条长程轨迹完成审计与增强，增强数据训练后模型盲改次数下降约 38%、接口签名错位下降 62%、工具报错减半。这个项目里我负责过程监督注入与压缩恢复样本合成两个模块的设计与实现，也参与静态预筛指标构建与蒸馏结果归因。

**🏗️ 业界标准 pipeline**：

> 业界标准的长程轨迹数据治理走 `并行 rollout 采集 → 轨迹导出聚合 → 静态/语义过滤 → SFT 打包` 范式——过滤环节常见做法是「规则 + Judge 打分」，训练样本基本按原轨迹原样打包。本项目在三个环节做了改动：归因环节补「三层证据链 + 九类失败模式」（把失败定位到具体动作）；增强环节加两段（过程监督注入、压缩恢复样本合成）；效果报告用来源归因（得分与行为指标分开报告、增益按来源拆分）。

### 2.1 盲写指标的静态预筛与三处复用

> **🗣️ 话术——盲写指标**：盲写指标这块我负责计算方式的统一与流程接入。指标定义很直接：一条轨迹里「连续写、改操作之间没有任何验证调用」的最大次数——判定窗口内只有 Write/Edit，没有执行过测试或命令这类验证动作。实际分布上，判分通过的轨迹这个值中位数在 15 上下，判分失败且在收集期报错的轨迹中位数在 31 上下，区分度比最终得分还强。由于计算方式固定、成本为零，我把它复用到了三个地方：SFT 打包前的质量门、rollout 运行期超过阈值时的提醒、失败样本的预测特征。

**机制拆解**：

1. **指标定义与计算**（按真实实现）：

   ```python
   def max_blind_edits(messages) -> int:
       """最长连续「写/改」段长度——段内无任何 Bash/验证调用。"""
       cur = best = 0
       for msg in messages:
           for call in msg.get("tool_calls", []):
               name = call["function"]["name"]
               if name in ("Write", "Edit"):     # 写类操作 → 段长 +1
                   cur += 1
                   best = max(best, cur)
               elif name == "Bash":              # 出现验证 → 段清零
                   cur = 0
       return best
   ```

2. **分布与判别力**（实测）：

   | 轨迹分组 | 盲写指标中位数 |
   | --- | --- |
   | 判分通过 | 15 上下 |
   | 收集期报错 | 31 上下 |
   | 极端个例 | 接近 90（两百多条消息里 60 多次 Write、30 多次 Edit） |

   因果链清晰：连续写大量文件不回读验证 → 结构或 import 直接失败 → 自测测不出来（自测本身也是盲写产物）→ 判分环境收集期直接报错。

3. **三处复用**：

   - **SFT 静态质量门**：超过阈值（20 上下）的轨迹进修复队列或降权，不进主训练集；
   - **rollout 运行时节流**：训练/采集时运行期监测同一指标，超过阈值就在下一轮前插入一条「先执行一次 import 冒烟验证」的提醒——把治理从「事后过滤」提前到「运行中纠正」；
   - **失败预测**：作为静态特征参与「这条轨迹大概率会失败」的预测，用于资源调度（比如优先重投）。

4. **为什么值得复用**：在容器成本高的链路里（重放、复评都要起容器），这种「计算零成本、区分度强」的静态特征比多做一次复评便宜得多——这也是它在三处共用的直接原因。

### 2.2 九类失败模式的轨迹归因体系

> **🗣️ 话术——失败模式归因**：这块我参与的是把归因结论接入打包环节。归因本身是三层证据链：第一层看判分输出，逐条列出失败的断言和报错位置；第二层回到轨迹里找到是哪一步动作引入的；第三层把失败归纳成九类可复用的模式、标注严重度。九类里最突出的是「自测与判分验证方式不一致」——模型自写的测试与官方判分测试验证的不是同一件事，几乎覆盖了全部低分任务；我负责把这类归因结论做成五维评分卡、接入打包环节：判分通过率、收集期零错误、盲写指标、完成标记、答案获取零信号（一票否决），评 80 分以上进训练集、50–80 分进修复队列。

**机制拆解**：

1. **三层证据链**：

   | 层 | 数据源 | 回答的问题 |
   | --- | --- | --- |
   | 判分层 | 判分完整输出（断言、报错、file:line） | 哪几条测试失败、失败在哪一行 |
   | 轨迹层 | 轨迹消息序列（全局消息索引 `g{N}`） | 哪一步动作导致了这个失败 |
   | 归因层 | 前两层对齐后判定 | 属于哪一类失败模式、严重度多少 |

2. **九类失败模式**（摘要）：

   | 失败模式 | 定义 |
   | --- | --- |
   | 过早终止 | 验证幻觉导致提前收尾（以为已通过、实际从未执行验证） |
   | 未完成 | 从未宣告完成，等待输入或超时 |
   | 上下文截断 | 对话被截断，已定位的状态丢失 |
   | 导航陷阱 | 反复 ls/read 空转、缺少有效编辑 |
   | 盲改 | 连续多次写改、中间无任何验证 |
   | 依赖与包结构失败 | 漏 `__init__.py`、包布局错误、import 失败 |
   | **验证方式不一致** | 自测与判分的验证方式不同（最主要的失效模式，几乎覆盖全部低分任务） |
   | 资源耗尽 | OOM / 内存不足 |
   | 答案获取 | 获取目标源码或判分材料 |

3. **两条统计维度**：频率与危害分开统计——「验证方式不一致」「盲改」几乎无处不在（高频率），但命中它的样本均分不是最低；「未完成」只出现个位数次，但命中的样本均分不足一成（低频高危）。零分任务几乎全出自两种组合：`验证方式不一致 + 依赖失败`（收集期报错）或 `验证方式不一致 + 过早终止`（自测全绿但契约错位）。
4. **五维评分卡**（接入打包环节）：

   | 维度 | 阈值标准 | 权重 |
   | --- | --- | --- |
   | 隐藏判分通过率 | 接近全过 / 过半 / 不足一半三级 | 约一半 |
   | 判分收集期 | 零错误 | 约两成 |
   | 盲写指标 | 不超过 20 上下 | 约一成 |
   | 完成标记 | 有明确完成动作 | 约一成 |
   | 答案获取信号 | 零信号（一票否决） | 约一成 |

   综合分 80 以上进训练集、50–80 进修复队列、不足 50 重采或丢弃。

5. **统计纪律**：归因统计只对全量做，不对「按低分筛出的子集」做——先按结果筛子集、再统计成因，结论会出现系统性反转（子集排除了高分组，而某些行为恰好集中在高分区）。

### 2.3 关键决策点的过程监督注入

> **🗣️ 话术——过程监督注入**：过程监督注入是我负责设计的模块。要解决的是四类问题：假完成（宣告完成但从未执行验证）、盲写不验证、规划流于形式（建了待办清单但不执行）、压缩后表现退化。共同根因是模型对任务状态缺乏感知——它知道自己做过什么，但不知道还差什么、处在哪个阶段。所以注入的内容不是操作指导，而是对任务状态的回顾。做法是在九类触发点里选点——完成宣告点必定注入，那是整条轨迹最该被核对的一句话；注入点数量按轨迹长度自适应分配，避免单条轨迹注入过多；注入文本用自然口吻、不加结构化标注，只追加 content 字段、不改动工具调用配对。

**机制拆解**：

1. **触发点路由表**（9 主 + 2 fallback）：

   | 触发点 | 优先级 | 注入内容类型 |
   | --- | --- | --- |
   | 完成宣告（"任务完成/全部通过"类表述） | 最高，必注入 | 完成核对（还差什么、验证依据是什么） |
   | 报错到修复的拐点 | 次高 | 规划（先诊断再动手） |
   | 官方测试执行点（首次执行测试、最后一次的前一轮） | 高 | 完成核对 |
   | 任务阶段边界、任务分解完成后首开工 | 中 | 阶段规划、分解一致性 |
   | 盲写段首、段尾（连续写改后首次转向验证） | 中 | 验证提醒 |
   | token 突增点、重读密集点（fallback） | 低 | 完成核对 |

2. **为什么完成宣告点必定注入**：整条轨迹里最该被核对的一句话就是「我觉得完成了」。漏掉这个点等于放过「验证幻觉」的唯一入口——它不受采样数量限制、必定被注入。
3. **自适应采样预算**（防止注入点聚集 + 控制标注成本）：

   ```
   base = max(1, (n_cand * MAX_SAMPLES) // (n_cand + MAX_SAMPLES))   # 调和平均式
   长度加权：>100K 字符 +2；>50K 字符 +1
   eff_max = clamp(base, 1, MAX_SAMPLES)   # MAX_SAMPLES 取 10 上下
   gap = max(2, n_cand // (eff_max + 1))   # 候选注入点按间隔均分，避免聚集
   ```

   短轨迹少注、长轨迹多注；必注入点另行全选；单条轨迹实际平均注入 3–4 个点。

4. **注入文本风格约束**：`Write your thinking in English. Write naturally and directly.`——自然口吻、不用结构化标注。逐轮打标签（如「阶段：实现中」）与训练数据的自然形态不符，模型会学到复述标签格式，而不是形成对任务状态的判断；规划类注入同时提供「该点之后真实发生的动作」，让计划与真实进程对齐。
5. **写入约束**（保证样本结构完整）：

   - 注入只改 `messages[idx]["content"]`（前置拼接），**不触碰 `tool_calls`**——工具调用与其返回的配对（`tool_calls[].id ↔ tool_call_id`）是训练样本的结构基础，配对破坏会直接导致样本不可用；
   - 写入内容从完整轨迹存档恢复（从导出链路的截断版本写入，会丢失触发点之后的内容）；
   - 质量门用纯关键词判据（长度 + 目标词组 + 结论词组，零 LLM 调用）；**质量不达标时丢弃该注入点、保留整条轨迹**。

### 2.4 压缩恢复样本合成

> **🗣️ 话术——压缩恢复样本合成**：压缩样本合成是我负责设计的模块。要针对的问题很具体：真实长任务进行到一定长度会触发上下文压缩，而压缩之后模型表现明显下降——对照组里，压缩过的轨迹中位得分大约只有未压缩组的一半，典型表现是「凭记忆接着改」（不重读文件直接编辑）和「重读泥潭」（反复读同一批文件）。这个模块把完整长轨迹在压缩边界处切开、重建成多条独立的训练样本，让模型学会「压缩之后先重读、先验证」的行为。一个关键设计是切点位置：token 达到阈值后不立即切，继续往后找到第一个「重读或执行测试」的位置再切——因为原轨迹里，这种位置之后的动作天然就是正确的恢复反射；如果切在写操作之后，训练数据就变成了「压缩后接着盲写」，方向完全反了。

**机制拆解**：

1. **错误行为与目标**：

   | 错误行为 | 表现 | 目标行为 |
   | --- | --- | --- |
   | 记忆盲改 | 压缩后凭记忆直接编辑，不重读文件 | 先重读、后修改 |
   | 重读泥潭 | 反复读同一批文件，失去任务状态 | 快速重建「已做/待做」清单 |

2. **切点检测**（按真实实现）：

   ```
   逐轮累积 token 估算（len(text)//3 粗估，全链路统一算法）
   达阈值（5 万 token 量级）后并不立即切，向后查找第一个满足条件的轮 k：
     (a) k+1 轮是「重读或测试」轮：该轮 tool_calls 含 Read，
         或 Bash 命令含 pytest / run-tests.sh / unittest
     (b) 尾部剩余 ≥ MIN_TAIL_TURNS（默认 4）轮
   ```

   这样选取的原因：k+1 之后的动作天然是「压缩后先重读、先验证」的正确反射，B 段样本的后续动作因而零盲改；切点选错则会把相反的行为写进训练数据。

3. **N+1 段样本构成**：

   | 段 | 内容 |
   | --- | --- |
   | A 段（压缩前） | 原轨迹 `messages[:切点]` 原样截断，作为独立样本 |
   | B 段（压缩后） | 任务前缀 + 摘要消息对 + 尾部消息（含恢复引导） |

   一条长轨迹切出 N+1 条独立样本，批量扩增训练数据。
4. **摘要消息对**（对齐主流编码 Agent 的压缩消息形态）：两条系统提醒（最后一次 Read 的输入与结果，超长截断）+ CONTINUED_PREFIX + **9 段有损摘要**（主要诉求 / 关键技术概念 / 文件与代码段 / 错误与修复 / 问题解决过程 / 用户消息记录 / 待办任务 / 当前工作 / 下一步）+ 恢复指令（`Resume directly — do not acknowledge the summary...`）。
5. **恢复引导的禁词质量门**：注入文本不得出现 compaction / summary / context limit 等词——推理时运行环境的指令是「不要复述摘要」，训练数据里出现「我刚被压缩过」这类自指描述会造成训练与推理不一致。质量门另查长度 + 核验语义词（confirm / verify / check / re-read / before modifying / run the test）。
6. **结构约束**：切点只落在轮边界上，保证每段的工具调用配对完整（`assistant.tool_calls[].id` 与 `tool.tool_call_id` 一一对应）——一批轨迹切出 130 余段样本，全部无配对错误。

### 2.5 蒸馏对照与来源归因

> **🗣️ 话术——蒸馏对照与来源归因**：蒸馏对照这块我参与的是评测设置与归因统计。数据配方是三类轨迹混合：采集到的成功轨迹、修复产出的短轨迹、以及增强出的两类样本（过程监督版 + 压缩版）；训练时 assistant 消息计 loss、环境返回不计，长轨迹注意序列长度与显存。评测中遇到过一个典型案例，此后把它固定成纪律：总分变化必须按来源拆分——某次对照实验总分掉了十几分，表面看像训练失败，拆分后发现约七成的退步集中在训练前依赖答案获取拿到虚高的那批任务上（训练后该类行为被消除、虚高分回到真实水平），其余任务基本没动。所以报告里两类结论分开写：得分变化按来源拆分，行为指标（盲改、签名错位、工具报错）与得分分开报告。

**机制拆解**：

1. **数据配方与训练要点**：

   | 样本类型 | 来源 | 占比（示意） |
   | --- | --- | --- |
   | 成功轨迹 | 采集导出（过五维评分卡） | 主力 |
   | 修复轨迹 | 低分轨迹修复产出的短轨迹 | 补充 |
   | 过程监督版 | 关键决策点注入 | 增强 |
   | 压缩恢复版 | 压缩切分 N+1 段 | 增强 |

   训练时 `assistant` 计 loss、`user`/`tool` 不计；百轮量级长轨迹注意序列上限（128K）与显存分配。
2. **评测去污染**：训练任务库来自对公开生态的扫描，与公开基准存在仓库重叠 → 训练集按仓库名黑名单过滤后再评；评测在独立 held-out 集上进行。
3. **来源归因**（本项目的核心方法论）：

   | 拆分维度 | 示例结论 |
   | --- | --- |
   | 得分变化按来源拆分 | 某轮总分变化中约七成来自「答案获取行为被消除」的任务，其余任务持平 |
   | 增益同样按来源拆分 | 另一轮表面增益中约六成来自残留的答案获取行为——据此把答案获取扫描从「离线审计」提前到「SFT 打包环节」 |
   | 行为指标与得分分开报告 | 总分差异在噪声量级，但轨迹行为明显改善：盲改 −38%、接口签名错位 −62%、最长盲改 8 轮上下压至 4 轮上下、工具报错减半 |

4. **消融表述纪律**（写实验结论时的固定规则）：

   - 单 trial、`|Δ|` 不足 0.05 时降档表述为「趋势性」而非「确证性」；
   - 收益按「答案获取 / 非答案获取」拆分，不拆分会把答案获取带来的虚高当成训练效果；
   - 退步同样归因到具体样本组，只报总分会把多件事混成一句「训练失败」；
   - 轨迹行为指标与得分分开报——分数未动但行为质量明显改善是真实改善，应单独报告。
